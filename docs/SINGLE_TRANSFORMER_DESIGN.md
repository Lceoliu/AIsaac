# 单序列 transformer 模型设计（seq-v1）

只是设计稿，日期 2026-11-17。本文没有改任何代码，没有提交。
文中凡标“估算”的数字都没有实测，只用来判断量级。

## 0. 一页结论

- **形状**：每个决策（4 帧）经一个浅的帧编码器压成 1 个 token，整局的 token 按时间排成一条序列，交给一个大的因果 transformer（下称主干）。策略头和价值头读主干在当前 token 上的输出。
- **去掉的东西**：block 模型的 resampler、Writer、Reader、PageStore、pool、block_to_spatial 全部不要。旧模型的房间 token 和反馈 token 默认也不要，留作对照开关。
- **输入和动作**：直接按 11-12 定下的兼容 Repentance 的新格式（visible-v3）做，不再在 v2 上做一遍。第 2 节逐条列出之前定了但没做完的要求。
- **为什么是这个形状**：
  - 这个骨架（帧编码器 + 每决策一个 token 的时间 transformer）就是旧模型的骨架，旧模型在 400 游戏小时里能学会（清房≥1 占比 0.48–0.51），block 模型的 400 小时臂全都学不会（0.17–0.25）。
  - 主干每个决策只处理 1 个 token，算力很便宜，大小和窗口长度可以当成变量来试（第 5 节）。
  - 关于“放大有没有用”，已有的证据是两面的：旧模型放大 1.5 倍（C100）前 12,000 游戏小时过层领先 1.5–3 倍，14,000–19,000 小时持平，25,000 小时的 512 种子定论反而低 0.18 层（1.006 对 1.19）。C100 条目自己的结论是“更大的模型只是起步更快，不支持把放大模型作为主线”。所以本设计不预设“越大越好”，大小由第 6 节的对照决定。窗口长度是 C100 没有测过的另一个变量。
- **不能省掉帧编码器**：一帧有 40–170 个异构对象（房间格子、身体、实体、道具、槽位），必须先压缩。真正“只有一个 transformer”的做法是把每帧的所有对象 token 都摊进序列，一小时会有 130–460 万个 token，整局上下文做不到。它作为备选方案 B 列在 3.6 节，不建议先做。
- **最大的未知**：visible 帧编码器（v2 和 v3）从来没有在一个能学会的模型里出现过。所以实验阶梯先分开验证主干和帧编码器，再合起来（第 6 节）。

## 3. 模型

### 3.1 总图

```
v3 帧（每决策一帧）
  -> 帧编码器：解码 + 空间 transformer（对象 token 之间）
  -> 取主身体 P token 和全局 token，线性投影成 1 个序列 token s_t（宽 D）
  -> 主干：因果 transformer，窗口 W 个决策，每个环境一份 K/V 环形缓存
  -> h_t = norm(主干在 t 的输出)
  -> 策略头 22、价值头、全局价值头、危险头 9、aux 头
```

### 3.2 帧编码器

- 输入解码按 `schema_v3.py`：房间画布卷积成 28 个 R token，小地图 M，全局 G，每个身体 P + 局部 9×9 块 L，实体 E，库存 N，槽位 S。线上是原始单位，模型里用冻结的缩放向量。这顺带消除了 v2 里“实体输入多除了一次 64”的问题。
- 空间 transformer 先保持现在的大小（宽 192，4 层 4 头），它不是这次要放大的部分。
- **读出**：取主身体的 P token（过完空间 transformer 之后的）和全局 token，拼起来过一个线性层得到 s_t。这是旧模型的读法。不用 resampler，不用学习的查询向量。
- **坐标**：全部按第 9 节的坐标契约做（一个参考系、各向同性、缩放只一次、相对量由模型在解码时算）。相对量是我们加的归纳偏置，开关 `--seq-rel-coords`，默认开，阶梯里做一次对照。
- pending（上一步动作，22 维）已经是帧输入的一部分，所以不需要单独的动作 token，一决策一 token 成立。

### 3.3 主干

- pre-LN 因果 transformer，注意力用 SDPA。
- 位置：旋转位置编码（RoPE），位置 = 局内的决策序号。K 在写进缓存时按自己的位置旋转一次，之后不用重算。旧模型是“每个头一张 0..W-1 的相对偏置表”，窗口放大后不合适。
- 局与局之间不互相看（按局号做掩码），和旧模型一样。
- s_t 走残差流直达输出，所以当前帧的信息一定能到策略头。这一点做成开训前的硬检查（6.1 节）。

大小档位（主干参数约 12·D²·层数）：

| 档 | 宽 D | 层 | 头 | 主干参数 | 每 token 的 K/V 缓存（bf16） |
|---|---|---|---|---|---|
| 旧模型时间侧 | 256 | 4 | 4 | 约 3.2M | 4.1 KB |
| S | 256 | 8 | 4 | 约 6.3M | 8.2 KB |
| M | 384 | 12 | 6 | 约 21M | 18.4 KB |
| L | 512 | 16 | 8 | 约 50M | 32.8 KB |
| GPT-2 small 大小 | 768 | 12 | 12 | 约 85M | 36.9 KB |

### 3.4 上下文窗口 W

- 一个游戏小时是 27,000 个决策，也就是 27,000 个 token。
- W 是一个可调的数，不是结构。起点 256（和旧模型一样），然后 1024、4096，最后才是整局。
- 整局上下文的约束不在算力，在 actor 那张卡的显存（第 5 节）：S 档每个环境每小时约 221 MB，GPT-2 small 档约 1 GB。
- 窗口以外的历史默认直接看不到。旧模型用房间 token 补这一块（每进一个房间留一个 token，全局可见）。本设计默认不要，开关 `--seq-rooms N` 留着做对照：如果纯窗口在同样小时数上不输，就不要它。

### 3.5 头

- 策略头：`Linear(D, 22)`，六个头（9, 5, 2, 2, 2, 2），使用类的头初始偏置 -4（和现在一样）。
- 价值头、全局价值头、危险头（9）、aux 头（1 步和 8 步）、特权 critic 都读 h_t，接口不变。
- 动作门常开（R12），留 `ISAAC_BLOCK_GATE` 那样的诊断开关。

### 3.6 备选方案 B：把每帧所有对象都摊进一条序列

- 做法：不要帧编码器的读出，每帧 40–170 个 token 全部进主干。
- 代价：一小时 130–460 万 token。窗口只能按帧数算，64 帧就是 3,000–10,000 token，记忆长度反而比方案 A 短两个量级，算力高一到两个量级。
- 结论：不先做。等方案 A 有结果、且有证据表明“每帧压成 1 个 token”是瓶颈时再考虑。中间形态是每帧 K 个 token（K = 2 或 4），开关 `--seq-tokens K`，默认 1。

### 3.7 与人类录像的关系

- 录像转成 v3 帧后就是（观测，动作）序列，单序列模型可以直接做行为克隆预训练。目前录像格式没有任何训练端在用。
- 这不在第一批实验里，只是说明这个形状给它留了位置。

## 4. 训练和工程

### 4.1 actor

- 每个环境槽一份环形 K/V 缓存：`[层, 2, 槽+1, 头, W, 头维]`，bf16，形状固定。旧模型的 TemporalState 已经是这个做法（W = 256，加 128 个房间位），并且能被 CUDA 图回放捕获。新模型是把它放大并去掉房间位。
- 所有槽一次 SDPA。新 token 的 K/V 就地写入。
- fork（教师、CF 分支、lane）需要复制父槽的缓存。复制量随 W 线性增长，S 档 W = 4096 时每次 33 MB，要实测对吞吐的影响。
- C++ driver、原生 consumer、lane 合并都保留。要改的是 driver 里和 block 页存储耦合的部分，以及 v3 的布局常量。

### 4.2 learner

- 片段：同一个槽里连续的决策，长度 T（256 起，可到 2048）。片段内带梯度；片段之前的 W-1 个决策用 actor 存下来的 K/V，不带梯度。这也是旧模型的做法。
- 梯度范围 = 片段长度，读的范围 = W，符合 R13。
- **历史新鲜度**：缓存里的 K/V 是用旧权重算的。W 越大，缓存里越老的权重越多（W = 4096、每槽每次更新 256 步时，最老的差 16 次更新）。旧模型在 W = 256 时带着这个近似能学会。W 放大后是否有害要实验回答。
- 可选的刷新 `--seq-refresh trunk`：每次换权重后，用存下的 s_t 把每个槽最近 W 个 token 重新过一遍主干。估算：128 槽 × 4096 token，S 档不到 1 秒。帧编码器那一半不刷新。默认关，放大 W 时做对照。
- 同步 K 个 shard 的梯度、分离 actor 卡和 learner 卡的做法都不变。

### 4.3 可以删掉的代码

block 页存储、Writer / Reader、版本化的图和延迟梯度、历史重算块。删不删、何时删等新模型过了第 6 节的阶梯再定，在那之前 block 的代码原样保留、不再投入。

## 5. 算力和内存估算（都未实测）

| 项目 | 估算 |
|---|---|
| 帧编码器每决策 | 约 55 个 token × 4 层 × 12·192² ≈ 1 亿次乘加 |
| S 档主干每决策，W = 256 | 约 700 万次乘加 |
| S 档主干每决策，W = 4096 | 约 1,500 万次乘加 |
| GPT-2 small 档主干每决策，W = 4096 | 约 1.2 亿次乘加，和帧编码器同量级 |
| learner 每次更新（32,768 决策 × 3 轮） | S 档主干不到 1 秒；GPT-2 small 档和帧编码器相当，约使更新时间翻倍 |
| actor 缓存，128 个槽，S 档 | W = 256：0.27 GB；W = 4096：4.3 GB；整小时：28 GB（超过一张 3090） |
| actor 缓存，128 个槽，M 档 | W = 4096：9.7 GB |
| actor 每步读缓存的内存流量，128 槽，W = 4096 | S 档约 4 GB，约 5 毫秒；GPT-2 small 档约 19 GB，约 20 毫秒 |

读法：

- 主干的乘加不是瓶颈，S 到 M 档几乎不增加每决策的计算。
- 真正随 W 和宽度涨的是 actor 侧读缓存的内存流量和显存。所以 W 和档位要一起实测，不能只看参数量。
- 整局上下文在 S 档需要把 actor 的槽分到多张卡，或减少每卡的槽数。这是后面的放大变量，不是第一步。

## 6. 实验阶梯

所有臂的读数不变：u201–330 清房≥1 占比 ≥ 0.35 算学会；对照是旧模型的 0.48–0.51；之后做 128 局评测。每臂 400 游戏小时。

### 6.1 第 0 步：开训前检查（不花 GPU 小时）

对每个新模型在随机初始化时测策略头输入：

- 状态相关的方差占比、相邻步变化量；
- 线性探针：玩家 x、门方向、敌人象限。

要求不低于旧模型初始化时的水平（旧模型：方差占比 0.366，x 的 R² 0.612，门 0.258 对基线 0.172）。block 模型在这一步就会被拦下（0.104 / -0.107 / 0.165 对基线 0.225）。

### 6.2 第 1 步：主干单独验证（用旧模型的帧编码器，现在就能做）

在旧模型代码上改主干，输入还是旧的 ROW 观测，这样帧编码器是已知能学的。

| 臂 | 改动 | 回答的问题 |
|---|---|---|
| T0 | 旧模型原样 | 已有：0.483 / 0.506 / 0.493 |
| T1 | 去掉房间 token 和反馈 token | 纯窗口的单序列主干够不够 |
| T2 | T1 + 主干 8 层（S 档） | 加深有没有用 |
| T3 | T2 + W = 1024 | 加长窗口有没有用，历史新鲜度有没有害 |

旧模型走 Python actor，约 184 倍，每臂约 2.2 小时。

### 6.3 第 2 步：visible 帧编码器单独验证

- 已经在跑的 rt-h2f 就是这个问题的一半：block 模型里把“空间 transformer 之后的玩家 token”直连到策略头。学会了，说明 v2 帧编码器给出的玩家 token 够用。
- 另一半：v2 帧编码器 + 旧的时间 transformer（不经过任何 block 部件）。需要让旧 actor 路径接受 visible 帧，是一段不大的代码。
- 如果两者都学不会，问题在 visible 帧编码器本身（比如没有相对坐标），先在这里修好，再做 v3。

### 6.4 第 3 步：合起来（v3 帧编码器 + 新主干）

- 前提：v3 的 A 包和 C 包完成，通过设计稿的 9 步验收。
- 先 S 档、W = 256、400 小时，对旧模型的 0.48–0.51。
- 然后放大：档位 S / M / L 和 W 256 / 1024 / 4096，每格 400–1,200 小时，按同游戏小时的读数和每秒帧数一起比。
- 相对坐标开关、K = 1 对 K = 4、刷新开关各做一次对照。

### 6.5 第 4 步：正式长训

- 按 R16 的设置从零训练，大小和 W 取第 3 步里最好的一格。

### 9.1a 引擎实测（V1，2026-11-17，8x3090 主机，AB+ 引擎）

cpp-actor 的探针测了 12 种房型各 3 个房间（36 个，0 错误）。下面的数是协调方用自己的脚本从原始文件 `rooms.jsonl` / `walk.jsonl` 复算的。

| 项目 | 结果 |
|---|---|
| 0 号格格心 `GetGridPosition(0)` | 36 个房间全是 (40, 120)，所以 0 号格左上角 O = (20, 100) |
| 格心规律 | 每一格都是 O + 40·(列 + 0.5, 行 + 0.5)，最大偏差 0.0000；行优先，宽度 = 网格宽 |
| 网格尺寸 | 1×1、IH、IV：15×9；1×2、IIV：15×16；2×1、IIH：28×9；2×2 和四种 L 形：28×16 |
| `GetTopLeftPos` 减 O（按格） | 1×1、1×2、2×1、2×2、四种 L 形：(1, 1)；IH、IIH：(1, 3)；IV、IIV：(5, 1)。**随房型变** |
| L 形 | 包围盒同 2×2，缺的象限分别是左上、右上、左下、右下；`GetTopLeftPos` 给的是包围盒左上角 |
| 逐帧格号 | 84,211 个本房间内的帧里，公式 floor((位置 - O) / 40) 与 `GetGridIndex` 只有 1 帧不同（y 恰在格边界上，输出四舍五入所致）；出网格 0 帧 |
| 实体与玩家同系 | 36 个房间各在已知位置生成一枚硬币，实际位置与请求位置全部相同，格号一致 |
| 网格外的实体 | 712 个实体里有 9 个在网格之外（房间上方的特效、网格下沿外几像素的实体），引擎对它们返回格号 -1 |
| 玩家位置范围 | 最小约在 0 号列 / 0 号行的门框里（相对 O 约 19–22 像素），没有出过网格 |

结论：

- F4 属实。v2 用 `GetTopLeftPos` 作原点，窄房间里位置和地形纵向差 2 格（IH、IIH）或横向差 4 格（IV、IIV）。
- 0 号格左上角可以作为所有房型的统一原点，C1 成立。
- 实体可以在网格之外，位置可以是负的。缩放和相对量不受影响，但“所在格”对它们没有定义，V3 的对齐测试和 C9 的范围表都要包含这种情况。
