    - 标准单房战斗继续参与 PPO：用当前策略重新采样，保留原来的任务分布与奖励，让网络继续优化真实战斗能力。

    - 连续房间里的新战斗状态（低血量、不同入口位置）不施加同样强的 C39 约束：它们本来就需要适应，不能一边要求适应、一边强制模仿旧策略。
    - 目标函数：L = L_PPO^{single, chain, goto} + λ·E_{s∼D_single} KL(π_C39(·|s) ‖ π_new(·|s, COMBAT))。关键是按**样本来源**（标准单房 / 连续房间战斗 / GOTO）区分，不是只按 COMBAT 掩码；buffer 里每个样本要带来源标记。
    - 单房 PPO 保住任务能力，KL 保住已有策略，两者不能互相替代。KL 默认保留，不预设最终降到 0。共享 critic 通过单房的真实回报继续训练，不强行复制旧价值输出。
15. **对塑形表述的更正**（用户指出，取代正文和前一轮回复里的说法）：
    - 恒定的是**折扣**塑形总和：Σ_{t=0}^{T−1} γ^t F_t = γ^T Φ(s_T) − Φ(s_0) = −Φ(s_0)（所有真正终局 Φ = 0），不是未折扣的普通求和。对相同起点、使用同一个 γ 并完整结算的轨迹，它保证塑形不改变基础任务的最优策略。
    - 它不保证整个奖励“没有可钻的空子”：成功判据、资源成本、失败代价仍然定义着基础任务，塑形只是不额外改变这个任务。
    - 提前失败的时间成本：当前步结算、还剩 N 个本来要执行的决策时，在当前 reward 里额外扣 −c·γ·(1 − γ^N)/(1 − γ)，才与未来 N 步各付 −c 的折扣时间成本一致；直接扣 −c·N 在 γ < 1 时只是近似。一致的只是时间成本部分，受伤、资源消耗不同时总回报仍然不同。这个补扣的含义是“提前失败不退还剩余时间预算”，不是要求所有失败方式价值相同。
16. **GOTO 里用炸弹**：炸弹数量自然继承到 B；地形改变以后重新计算距离场；塑形用旧状态在旧地图上的旧势值、新状态在新地图上的新势值，F = γΦ_new(s′) − Φ_old(s)，不能用新地图反算旧状态、覆盖之前的势。

17. **道具头“全部打开”的口径**：按引擎可用性遮罩，手里有可用的主动道具时才能按，和环境自己的 `action_masks` 一致（取代 `gpu_ppo.py:99` 的恒遮）。现在不给道具，所以实际仍全遮：COMBAT 逐位不变，KL 不受影响；以后给了道具这个头自动放开。
18. **所有 COMBAT 的受伤价格统一为每半心 −0.1**：标准单房战斗也从 C39 的 −0.05 改成 −0.1（即 combat-hp2 的 hurt=1.0），与链里的战斗、GOTO、C41 一致，共享 critic 只看到一种价格。已知代价：单房奖励与 C39 训练时不再完全相同，KL 锚会和新奖励有一点拉扯。

### COMBAT 途中出门（2026-09-30 定案；引擎事实见 EXPERIMENTS.md A13）

用户决定：出门不结束 COMBAT，也不加限制。反复进出拿伤害奖励、在别的房间打怪都算合理玩法：多房间的链里这本来就合理；单房任务有炸弹数和时限，刷不起来，这种学习能力反而值得鼓励。只修一个 bug：出门以后被误判为清房。

| 情形 | 结局 / 奖励 |
|---|---|
| 在目标房 T（option 开始的房间）里清房 | 胜，+100（同原来） |
| 从 T 出去（炸开的门） | option 继续，历史窗口从新房间重新开始，option 的时钟不重置（`VisibleHistory.room_clear`） |
| 在别的房间（包括本来就清空的起始房），或者别的房间被清掉 | 不算胜；伤害、掉血照常计（奖励不改） |
| 回到 T 清房 | 胜 |
| 清房倒计时内离开 T，引擎把 T 记为已清 | 胜（不在 T 时查 T 的 `RoomDescriptor.Clear`）；链的后续 option 属于 T，序列就此结束 |
| 死亡 / 时限到 | 同原来（−100） |
| 单房训练的 goto 房出门 | 同上：option 继续，进的是楼层里的真实房间，回不去，最后超时 |

## 1. 一句话目标与第一个里程碑

**目标**：把策略从 π(a_t｜s≤t) 扩成 π(a_t｜s≤t, g)。g 是当前 option 的目标，包括 COMBAT、GOTO_POSITION、GOTO_DOOR，以后还有 GOTO_PICKUP 等。低层只负责当前房间，穿门就结束当前 option。在 COMBAT 上保持与现有模型（π_old = C39 最终）一致，同时让同一个网络学会房内导航。

**第一个里程碑：真实楼层上的 1×1 两房间链。**
1. A 房（1×1 战斗房）COMBAT，直到清房；
2. 控制器随机选一扇能走的门；
3. GOTO_DOOR 走过去；
4. 引擎真实换房，进入 B 房（A 的 1×1 战斗邻居）；
5. B 房 COMBAT，直到清房。

先用脚本导航把整条链跑通（链 v0，不改模型），再把导航换成学出来的 GOTO。

## 2. 整理后的方案

标注的含义：**采纳** = 照用户原意做；**修改** = 方向保留，做法改；**待定** = 推迟，或者要先拿到证据。

### 2.1 目标编码

| 用户原意 | 标注 | 改成什么 |
|---|---|---|
| g = [e_task, Δx, Δy]，可以再加 d 或 (d, sinθ, cosθ) | 修改 | 每帧写一个 f4 字段 `goal`，共 14 维，逐项见本表下方的列表 |
| COMBAT 时 d = 0 | 修改 | COMBAT 帧只写 one-hot[COMBAT]=1，其余全为 0。网络里用硬门控 `gate = 非 COMBAT`（`torch.where`）把目标分支隔开。d=0 会和"GOTO 已到达"混淆，而且极坐标在 d=0 时没有定义 |
| 坐标不告诉路线 | 采纳 | 绕障碍的最短路距离 d_geo 只给 critic，放在新字段 `goal_distance` = d_geo/40。这沿用 fire_distance 只进 critic 的原则（`transformer_policy.py:9-12`、`:212-216`）。规划器的输出（8 个邻格的 d_geo、最短路的下一步）都不进 actor |
| 任务类型：GOTO_POSITION / GOTO_DOOR / GOTO_PICKUP / COMBAT | 采纳 | 第一个里程碑只用 COMBAT、GOTO_POSITION、GOTO_DOOR。one-hot 留了空槽，以后加任务不用改第一层 |

`goal` 字段的 14 维：
- 8 个任务 one-hot 槽：COMBAT、GOTO_POSITION、GOTO_DOOR、GOTO_PICKUP，另 4 个预留；
- dx/520、dy/280：和实体的 dx、dy 用同一单位（`transformer_obs.py:265`）；
- d/520：像素距离；
- sinθ、cosθ：在像素空间里算，d<1 px 时写 (0,0)；
- in_window：目标格是否在 15×9 窗口内。

每一帧都按玩家当前位置重算这些量（以玩家为原点），不做在线归一化。worker 必须断言所有字段都是有限值。

### 2.2 模型改动（5 项）

| # | 用户原意 | 标注 | 改成什么 |
|---|---|---|---|
| 1 | 镜头模式下，玩家位置改成相对窗口 | 采纳，作为独立开关 | 见本表下方第 1 项 |
| 2 | Q = Q_learned + W_p h_player + W_g h_goal | 修改 | 保留这一项作为辅助通路：零初始化的 Linear(64→128)，乘门控。主通路改到 fusion 的 LayerNorm 之前，加上 `gate·goal_fusion(h_goal)`，goal_fusion 是零初始化的 Linear(64→256)。原因：只靠 query 注入时，没有实体的帧里目标完全看不到（实测输出差 0.000）；有实体时，key 和 value 里也不带目标坐标 |
| 3 | 地形加一张目标图（原文写的 7×9×16，应为 8×9×15） | 修改 | 见本表下方第 3 项 |
| 4 | option 切换时清空 64 步历史 | 采纳并细化 | 见本表下方第 4 项 |
| 5 | 保留局部 CNN，另加 16×28 的全房间拓扑分支 | 待定（推迟到大房间） | 见本表下方第 5 项 |

**第 1 项：窗口相对位置。**
- 在 `room_scale=='camera'` 时：
  - x = (px − (left + 40·col0)) / 520；
  - y = (py − (top + 40·row0)) / 280；
  - 其中 (row0, col0) = `camera_origin`。要把窗口原点的计算从 `transformer_obs.py:309` 挪到 `:239` 之前。
- 凡是 15×9 网格的房（1×1、IH、IV），col0 = row0 = 0，改了以后逐位不变，由 `test_c41.py:95-101` 守住。
- 它对 1×1 两房链没有作用，效果只在大房间那条线（M5）里评估。到那时还要补上 (col0, row0) 或全房间分支，否则网络不知道自己在整个房间里的位置。

**第 3 项：目标图。**
- 不改 `terrain`，另外新增一个 `goal_map`，形状 (2,9,15)，f4：
  - ch0：目标所在格；
  - ch1：**开着的门**所在格。
- 它经过一个零初始化、无 bias 的 Conv2d(2→16, 3, padding 1)，加到 `map_cnn[0]` 的输出上，再接 `map_cnn[1:]`。
- 数学上，这等于第一层卷积多了两个输入通道。但另开一个 key 有四个好处：
  - 不碰基础 FRAME_DTYPE，也就是模拟器的 ABI；
  - 逐位不变不依赖 GPU 对补零通道的处理（这一点没有验证）；
  - π_old 的 Conv2d(7) 仍然能吃同一份 obs；
  - Adam 状态可以按名字原样迁移。

**第 4 项：清历史。**
- option 的边界就是 PPO episode 的边界（terminated）。
- 换房进 B 时硬清空，调用 `VisibleHistory.clear()`。
- 同一房间里的 COMBAT→GOTO、GOTO→GOTO，用一个新写的软清空：清掉窗口、时间原点、combat 基线和上一个动作，但保留上一帧的原始观测，这样速度差分仍然有效。
- 64 步是 256 个逻辑帧，约 8.5 秒，不是 4 秒。

**第 5 项：全房间分支。**
- 1×1 房里，15×9 的窗口就是整个房间，静态地形是重复的。唯一新增的信息是"开着的门在哪"，这由 goal_map 的 ch1 提供。
- 设计先定下来，代码推迟：
  - 输入 `room_bits`：16×28 的 i4，每格按位打包 8 个通道，即 inside、walkable、hazard、destructible、door、player、goal、window；
  - 结构：3 层卷积 + FC(896→128)，再经零初始化的 Linear(128→256) 接进 fusion；
  - 参数 129,872 + 33,024；每帧约 1.44M MAC；帧记录多 1,792 B。

### 2.3 GOTO 训练

| 用户原意 | 标注 | 改成什么 |
|---|---|---|
| 随机 1×1 房、随机障碍布局 | 修改 | 只用引擎里真实存在的房间，不自己生成布局。房间来源见本表下方。按房间 variant 留出约 20% 测泛化 |
| 随机出生点 S、随机可达目标 G | 修改 | 候选格：玩家所在连通块内、可走、不是尖刺、d_geo ≥ 2 格的格子中心。按直线、绕路、死角三类分层混合：仿照 `target_cells_walkable` 的抽样流程，但用 goal_field 重新定义分层（它的 `detour_min`/`trap_min` 量的是走到射击位置的距离，不是走到目标格，`abplus.py:331-377`）。绕路 = d_geo − 直线距离 ≥ 1 格；死角 = 从起点朝目标直线走会进入深度 ≥ 30 px 的死胡同（仿 `trap_depth`，改用 goal_field）。目标序列由 (seed, k) 决定。每加载一次房间给 K=8–16 个目标 |
| 到达即成功 | 修改 | GOTO_POSITION：相邻两次决策之间的线段，到目标的距离 ≤ R（建议 20 px）就算到达，因为一步能走 30–41 px。GOTO_DOOR：引擎发生换房，而且 `Level.LeaveDoor` 等于目标门槽 |
| r = −c/步，到达 +1，进度项 α[d_t − d_{t+1}]，d 用 d_geo | 修改（数值由用户定） | 改用标准势函数 γΦ(s′)−Φ(s)，Φ = −α·d_geo/40，γ = 学习端的 0.999。失败终局不结清 Φ；出门、走错门另算代价。见 4.7 |
| 用 d_geo 而不是欧氏距离 | 采纳 | 新写 `goal_field`，以目标格为唯一源点，沿用 `walk_grid` 的 8 邻接、不斜穿拐角。去掉 600 px 的封顶；尖刺格加代价；火堆（实体类型 33）当作阻挡 |

goal_field 的三个边界情况：
1. **门格不可走**：门格 inside=0、walkable=0，门开着也一样（`abplus_geometry.py:177`）。GOTO_DOOR 以门内侧相邻的可走格为源点；成功仍按换房和 LeaveDoor 判定。
2. **场里找不到玩家**：玩家所在格和邻格都不在场里时（现在靠 600 px 封顶兜底，`abplus_geometry.py:224-238`），沿用上一帧的 d_geo 并计数。不要用断言：worker 会把任何异常当成引擎故障，重启游戏进程（`abplus_worker.py:728-736`）。只在非有限值写进帧之前替换并记数。
3. **地形会变**：射击不遮，眼泪能打掉便便、浇灭火堆。场按地形 version 加火堆集合缓存，变了就重算，这样 Φ 才只取决于当前状态。

GOTO 的房间来源：
1. **战斗后的尾段**：现有战斗组清房以后，不重置，在同一个房间里原地接 K 个目标。这就是真实的清房后状态：门开着，有清房奖励的掉落物，还有残留弹幕。
2. **空房组**：第四档的 428 个障碍房（`catalog/mixture_target_tier4.json`），删掉玩家以外的所有实体。
3. **GOTO_DOOR**：放在真实楼层里删空的房间练，这样有干扰门。

### 2.4 保护战斗能力

| 用户原意 | 标注 | 改成什么 |
|---|---|---|
| 保存一个冻结的 π_old，π_new ← π_old | 采纳 | π_old = C39 最终。阶段 2 开始时把网络 deepcopy 一份并冻结，当作老师（见 4.8）。零初始化加门控保证它在 COMBAT 上逐位等于 C39；它在 GOTO 帧上的输出不进任何损失 |
| 阶段 1 只训 goal encoder、fusion adapter、critic，必要时加 actor 最后一两层；state encoder 冻结 | 修改 | 冻结**全部**共享参数，包括编码器、fusion、temporal、policy_net/action_net、COMBAT 的 value 头和 aux 头。只训门控的新模块和 GOTO 专用的 value 头。容量不够时，加门控 LoRA（policy_net 上秩 16，B 置零）或门控的残差 actor adapter。这样 COMBAT 的输出在构造上就逐位等于 π_old，阶段 1 不需要 COMBAT 样本，也不需要 L_preserve。原方案里"训 critic、训 actor 最后几层"会直接改动 COMBAT |
| 阶段 2 联合训练，COMBAT:GOTO 约 70:30 或 50:50 | 采纳（有条件） | 只在两种情况下开：阶段 1 不过验收；或者两房链暴露出只有联合训练才能补的缺口。用 `--budget slots`，32 个槽里 22 个 COMBAT（C39 的四组）、10 个 GOTO，约 69:31。COMBAT 严格沿用 C39 的设置：combat-hp、scaling_groups、满血、1 个炸弹、Room Buffer |
| COMBAT 用 R_combat，GOTO 用 R_goto | 采纳 | option 当作 episode 以后，两种回报自然分开。另外按任务分 value 头，按任务分别归一化优势 |
| L = L_PPO + λ·KL(π_old ‖ π_new(·｜s, COMBAT)) | 采纳 | 复用 gpu_ppo 里现成的蒸馏通路，改成：只对 COMBAT 样本算、按 COMBAT 样本数归一、老师 logits 每轮只算一次并缓存、`--distill-rl-coef 1` |
| 稳定后 λ 逐步降到 0 | 修改 | 用自适应 λ，把 COMBAT 上的累计 KL 压在目标 0.05 以下。大评估通过以后才放宽或降到 0；COMBAT 数据始终保留 |

阶段 2 与 C39 做不到完全一样的两处：
- **Room Buffer**：`--warm-start` 不恢复 Room Buffer（`train_abplus.py:1167-1175` 只在 `--resume` 时读 `room_buffer.json`），缓冲区从空开始，而 C40 的混杂因素里正好有这一项。要么新加参数从 C39 checkpoint 读 `room_buffer.json`（组名要一致），要么把它写进差异。
- **组份额**：C39 四组按步数各 25%；slots 下 22 个 COMBAT 槽只能分成 6/6/5/5（`abplus_groups.py:77-88`），约 27/27/23/23%。可以改成 COMBAT 24 槽（每组 6 个）+ GOTO 8 槽，约 75:25。

### 2.5 两房间链

| 用户原意 | 标注 | 改成什么 |
|---|---|---|
| Room A combat → 随机指定 Door → navigate → Room B combat → clear | 修改 | 只能在真实楼层上做。goto 加载的房间只有一扇门（入口），而且按静态分析，这扇门通回起始房 84。具体做法见本表下方 |

真实楼层上的两房链流程：
1. `restart 0` 生成一整层真实的 Basement I；
2. 用 Lua `GetRooms` 在线选出 A（起始房的邻居，1×1 普通战斗房）和 B（A 的 1×1 战斗邻居）；
3. 设 `LeaveDoor=slot`，再调用 `Game():StartRoomTransition(A, slot&3, 0)` 进 A；
4. A 清房后，真实穿门进 B。

## 4. 各项推荐做法与理由

### 4.0 推荐的网络改动一览

```
goal(14) ──► goal_encoder: Linear(14→64) GELU Linear(64→64) LN   [随机初始化，不能置零]
                 │ h_goal(64)
player(74) ─► player MLP ─► h_p(64)
entities ───► entity MLP ─► K,V ─┐
queries + player_query(h_p) + gate·goal_query(h_goal) ─► MHA ─► 4×128
                                     [goal_query 零初始化]
terrain(7,9,15) ─► map_cnn[0] + gate·goal_conv(goal_map(2,9,15)) ─► map_cnn[1:] ─► 128
                                     [goal_conv 零初始化，无 bias]
cat(736) ─► fusion[0] + gate·goal_fusion(h_goal) ─► LN ─► GELU ─► 256   (主通路)
                                     [goal_fusion 零初始化]
─► temporal(64 步，4 层) ─► policy_net [+ gate·LoRA，B 置零，可选] ─► action_net(18)
                         └─► TaskValue: where(gate, v_goto([latent, goal_distance]), v_combat)
```

- **门控**：`gate = goal[...,1:8].sum(-1) > 0`，用 `torch.where` 实现。
- **COMBAT 行不变的原因**：门控为 0 时，每个注入点加的都是精确的 +0.0，原有算子的输入和形状都不变，所以 COMBAT 行永远与目标分支的参数无关。
- **CPU 实测**：新模块训练 20 步、权重已经非零以后，下面这些 COMBAT 行仍与旧模型 `torch.equal`：纯 COMBAT 批次、COMBAT/GOTO 混合批次里的 COMBAT 行、完整的 64 步窗口，紧凑和静态两条编码路径都一样（核查 #6）。GPU 上还没有验证。
- **新增参数**，约 96.8k，占 +2.4%：
  - goal_encoder 5,248；
  - goal_fusion 16,640；
  - goal_query 8,320；
  - goal_conv 288；
  - GOTO value 头 66,305；
  - 门控 LoRA（可选）另加 8,192。
- **帧记录**：多 goal 56 B、goal_map 1,080 B、goal_distance 4 B，约 +1.5%。

### 4.1 两房间链的引擎方案（各视角一致）

| 方案 | 做法 | 评价 |
|---|---|---|
| (a) 真实楼层 | `restart 0` → `GetRooms` 在线选 A 和 B → `LeaveDoor=slot` + `StartRoomTransition(A, slot&3, 0)` 进 A（与门触发调用同一个函数、同一组参数）→ A 清房后真实穿门进 B | **推荐**。楼层、布局、门、邻接关系、刷怪都来自引擎本身。缺点是 Lua 的这几个接口桥从来没用过，要先做探针 P2 |
| (b) 碰门后再 goto | goto 进 A；A 只有入口一扇门，穿过去先回到起始房 84，再 goto 到 B | 备选。只能走进来的那扇门，所以 GOTO_DOOR 会学成"回入口"。拓扑和时序是拼出来的 |
| (c) 改写 goto 房门的 TargetRoomIndex | — | 不推荐，完全没有验证 |
| (d) 从起始房真实走门进 A | `restart 0` 以后把玩家放到起始房通往 A 的门内侧，脚本朝门走几帧，由引擎自己的 check_player_enter_door 换房；A 清房后同样真实穿门进 B | **(a) 的后备**。两次进房都走引擎原生路径，不依赖 StartRoomTransition。前提是起始房开局时门是开着的（推测，未验证，P2 一起核对） |

(a) 需要配套的改动：
- **不闩门**，至少跳过 variant 7（隐藏门）。`Bar()` 会把隐藏门改成 variant 4，清房时就会被打开（静态），这会改变游戏规则。
- **隐藏门不能进策略输入**：`obs.doors` 和通道 6 里要过滤掉还没被揭示的隐藏门，否则会违反 MACRO_PLANNING §1 的信息边界（推测，未验证；探针 P5）。
- **诅咒**：链模式在 `restart 0` 之后、任何 RemoveCurse 之前先读 `GetCurses()`，含 Labyrinth(0x2)、Lost(0x4) 或 Maze(0x20) 的楼层直接换种子，其余诅咒再移除。现有 ROOM_LUA 是先移除再核对（`abplus.py:149`、`:777-780`），核对永远通过；而 AB+ 生成器显示第 1 层也会掷出 Labyrinth 和 Lost（`rl/macro/isaac_macro/level.py:185-200`），它们在生成时就改了楼层布局，事后移除改不回来。Maze 的依据：`Level::ChangeRoom` 在 `GetCurses()&0x20` 时调用 `Random(10)`（`decompiled/03/0033BC00_ChangeRoom.c:54-57`，静态）。离线预筛同样按诅咒过滤。
- **楼层类型**：只接受 `stage_type==0` 的楼层（探针 P6）。
- **`GetRooms` 只给控制器用**：它包含隐藏房，只能用来选房，不能进策略输入。
- **离线预筛（可选）**：可以用 rl/macro 离线预筛种子，但要在装了 ABP_STARTSEED 的主机上才准。在线 `GetRooms` 才是准绳。

**选门口径**：生成器统计里"A 至少有 2 扇门可选"占 84%，但这个数包括回起始房的那扇门。如果只允许通往没清过的 1×1 战斗房的门，可选的门会更少，这个没有统计。所以：
- **GOTO_DOOR 训练**：目标可以是任意一扇开着的门，包括回起始房的门；
- **链评估**：目标取通往 B 的门。

### 4.2 目标注入方式（有分歧）

| 视角 | 主张 | 理由 | 代价 |
|---|---|---|---|
| 架构、训练 | 门控 + 零初始化的加法注入：fusion 的 LN 之前是主通路，另有 goal_map 卷积，query 项作辅助；配阶段 1 冻结 | 训练以后 COMBAT 仍然在构造上逐位不变；阶段 1 省掉 π_old 前向和 KL | 要改加载（非严格白名单）、Adam 按名对齐、另写 TaskValue |
| 红队 | 把目标做成实体集合里的伪实体 token：entity_type 取 1001–1023，dx/dy 相对玩家 | 零新参数，观测空间不变；严格热启动、101 项 Adam、`load_frozen_policy` 都能原样用；复用策略已经会的"看实体 dx/dy 绕障碍走位" | GOTO 帧里 softmax 被这个 token 分走一部分。通路上只有共享的实体 MLP 和嵌入行可以训练，和冻结不相容，只能一开始就联合训练加 KL。"1001–1023 这几行嵌入从没被训练过"只是推测 |
| 环境 | 没有偏向 | 要求 COMBAT 时目标特征全为 0，另给任务标志和门控 | — |
| 用户 | 只用 query 注入 + 地形第 8 通道 | — | query 在没有实体的帧里完全看不到目标（清房后的 GOTO 正是这种情况） |

**推荐：门控加法注入。** 理由：
- 用户的核心诉求是"加新技能时不忘旧技能"。结构上的保证比 KL 这种软约束更硬。
- 迁移要写的代码已经在 `rl/docs/goal_conditioned/arch_proto*.py` 里做过原型。
- 伪 token 方案留作两种情况下的备选：迁移工程出了意外，或者阶段 1 失败、要直接进入联合训练。

**不采用的方式**：
- FiLM：乘法调制的杠杆更大，不稳定的风险也更大，留作备用；
- 时间 Transformer 里加额外 token：前置 token 再 mask 掉会输出 NaN，不 mask 又做不到逐位不变。

### 4.3 阶段划分：先冻结，还是直接联合（有分歧）

| 视角 | 主张 |
|---|---|
| 架构、训练 | 阶段 1：门控 + 冻结全部共享参数，只训新模块和 GOTO value 头。阶段 2 有条件才开 |
| 红队 | 配合伪 token，跳过冻结，直接从 C39 联合训练，COMBAT 约 70%，KL 只加在 COMBAT 样本上，LR ≤ 1e-4。理由：π_old 已经保存了，联合训练最坏只是浪费算力 |
| 用户 | 先冻结 state encoder，训 goal encoder、fusion adapter、critic 和 actor 最后几层；再联合 |

**推荐：架构和训练视角的版本。** 用户原方案内部有矛盾：
- 共享的 critic 和 actor 头不受门控，训练它们就会改变 COMBAT；
- 只用 GOTO 数据训共享 critic，COMBAT 的价值估计会漂移，阶段 2 一开始 COMBAT 的优势就是错的。

阶段 1 的风险只在于冻结的主干能不能表达 GOTO，项目里没有冻结微调的先例（推测）。应对办法是 30 游戏小时做一次 go/no-go；不行就先加门控 LoRA 或残差 adapter，再不行就提前进入阶段 2。

### 4.4 option 边界与清历史

**option 边界 = PPO episode 边界（四个视角一致）。**
- 结束时写 `done=True`、terminated，不做自举。`reset_row` 写的是"当前原始观测，用新历史和新目标重新编码"的那一帧。
- 学习端一行不改：done 时 lengths 置 1（`gpu_ppo.py:681`），GAE 在 episode_starts 处切断。
- COMBAT 的 MDP 与 π_old 训练时完全一样：清房即 +10 终局。
- 另一种做法是"整条链算一个 episode，只重置历史"。那要加 `history_reset` 字段，还要按任务分 value 头或加 GAE 截断标志；A 清房处的 value 会从 GOTO 那一段自举，两种奖励混在一起，L_preserve 也会和 PPO 互相拉扯。不建议。
- 代价全在 worker 端：
  - done 以后不再换备用实例，而是原地续玩（`abplus_worker.py:738-791`）；
  - 局的计数和链的计数要分开，否则备用实例的 schedule 下标会错位；
  - 奖励对象按任务各建一个（现在是 `:579-583` 一个）；
  - OUTCOMES 末尾追加 `goal`、`exit`、`wrong_door`；
  - Room Buffer 不收链里的局；
  - `monstro_gym.py:138-151` 在链模式下要把换房当作 option 的结束，而不是 BridgeError；还要确认转场那一步会不会触发帧数检查（抛 RuntimeError，探针 P3）。
  - 每个 option 开始时调用 `option_begin`：重建奖励对象的基线、EpisodeStats、damage0 和 meta，进 B 以后把 layout 改成 B 的 variant。这些现在只在 `_begin` 里设（`abplus_worker.py:621-676`）；桥端 `zero_events` 只在 reset 命令里调用（`abp_bridge.lua:1311-1315`），`MC_POST_NEW_ROOM` 什么也不重置（`:1450-1453`）。真实走门进 B 时不跑设置脚本；谱系模式 3 下 B 的挡门怪第一次出现就会入名单（`abp_bridge.lua:641`），推测 combat 输入和掉血计数仍然正确，放进 P3 逐帧核对 B 的 combat 块和名单人数，不对就在进 B 的那一帧补调 `AbpRosterMark(3)`。

**硬清空和软清空（环境视角与架构视角的分歧，已合并）。**
- 架构视角要求所有切换都清空，因为 COMBAT 窗口里只能有 COMBAT 帧，逐位不变才成立。
- 环境视角指出，同一房间里切换时硬清空，会丢掉一个决策的玩家速度和全部弹幕速度（motion_valid=0），而这正是残留弹幕最多的时候。
- 合并后的规则：
  - 换房时硬清空。引擎本来就把速度清零了，不丢信息。
  - 同一房间里 COMBAT→GOTO、GOTO→GOTO 用软清空：只保留上一帧的原始观测，窗口里不含 COMBAT 帧。
  - COMBAT 一定是在换房之后开始，所以 COMBAT 永远是从硬清空开始的，逐位不变仍然成立。

**B 房入口（有分歧）。**
- 环境视角：空跑到 `room.frame ≥ 9` 再交给 COMBAT，并重设血量和炸弹、重播 MT，照 `_reset_room` 在 goto 前重播 MT 的做法（`abplus.py:722`）。
- 红队：先测量，再决定要不要人为延迟。
- 背景：训练开局的第一帧在房间加载后约 9 帧（8 帧等待 + 1 帧）；真实换房后，第一帧只晚 1–4 帧，而且这几帧里还按着 A 房最后的动作（静态推断）。
- **推荐**：在 M1 里做配对测量，四种组合都跑，因为很便宜：
  - 入口时机：立即接管，或空跑到第 9 帧；
  - 玩家状态：归一化，或延续 A 房的状态。
  - 用数据决定 M2–M4 的默认值。

### 4.5 critic、优势、aux 与动作遮罩（各视角一致）

- **critic 分头**：
  - COMBAT 用原来的 `value_net`，key 不变；GOTO 用新的 MLP(257→256→1)。
  - 接线：CombatTransformer 把 `goal_distance` 和 gate（最新帧的门控）两维，像 fire_distance 一样追加在每帧特征末尾，绕过 Transformer（`temporal_features` 的 extra 处理改成按附加维数判断，`transformer_policy.py:169-182`）。`SplitMlpExtractor.forward_critic` 只把前 257 维送进原来的 value MLP，保持 Linear(257,256)，C39 权重才能原样载入；再把 [latent_vf(256), goal_distance, gate] 交给 TaskValue。
  - TaskValue 的 COMBAT 分支就是原来的 `value_net`，GOTO 分支读冻结的 COMBAT value MLP（Tanh）的输出加 goal_distance。这样 5 处 `value_net(...)` 调用（`gpu_ppo.py:177`、`:187`、`:379`，`graph_sampler.py:120`、`:158`）和 CUDA graph 的 `_act` 才真的不用改。如果 30 h 时 GOTO 的解释方差偏低，改读 Transformer 输出的前 256 维。
  - 理由：两种回报的尺度大约差 10 倍（清房 +10，GOTO 到达 +1）；阶段 1 如果共用一个头，COMBAT 的逐位不变就保不住。
- **fire_distance**：它在 GOTO 里是一个没有信息的常数（开局取 15，或者停在清房那一刻的值）。GOTO 头用 `goal_distance` 代替它，COMBAT 头照旧。
- **优势按任务分别归一化**：`gpu_ppo.py:473-479` 改成按任务掩码分别算均值和标准差。不上 PopArt。某任务在 minibatch 里样本数 <2 时不做归一，一律用 `torch.where` 选择而不是掩码乘法（0×NaN=NaN 会污染整个 minibatch 的梯度）；单测覆盖只含一种任务的 minibatch。
- **aux 损失在 GOTO 样本上屏蔽**：`gpu_ppo.py:500-509`。GOTO 帧里 `aim_label` 恒为 0，不屏蔽的话会通过潜变量去推目标分支。
- **炸弹在 GOTO 帧上遮掉**：`action_masks`（`gpu_ppo.py:95-101`）里 `bombs_ok` 与"非 GOTO"取与。两个调用处 `gpu_ppo.py:181`、`graph_sampler.py:109` 都要传入任务信息。原因是炸弹会炸掉石头，改变 d_geo 和目标是否可达。GOTO 预训练时也可以直接设 bombs=0，现有遮罩会自动生效。射击不遮。
- **remaining_time**：每个 option 有自己的期限，1×1 房建议 8 秒（约 60 个决策）。超时当作终局，与 combat-hp 的做法一致。clear 和软清空都会把时间原点重置。

### 4.6 GOTO 的数据与吞吐

- **一次重置只配一个目标不划算**：1×1 房里一个 GOTO 目标平均约 7 个决策（约 70 ms 的 worker 时间），一次重置却要 160–230 ms，重置会吃掉约 2/3 的实例 CPU。
- **K 个目标连用**：每次加载连续给 K=8–16 个目标，重置开销就降到 20% 以下（估算）。战斗后的尾段完全不增加重置，而且就是链里 GOTO 真正面对的状态分布。
- **空房的门**（静态推断）：没有挡门实体时，引擎约 10 帧后自动清房，每帧对所有门调 Open，还会 `SpawnClearAward`。`Bar()` 挡不住。**推荐**：接受门会开，从门出去就是失败结局 `exit`。每帧调用 `KeepDoorsClosed` 只作为备选，要先经探针 P4 验证。
- **d_geo 训练前的引擎核验**：在引擎里用脚本沿 d_geo 贪心下降，跑 1–2 千个 (S, G)，统计可达率和用时。这个脚本同时是 SPL 的参照，也是链 v0 的导航器。
- **已知的几何误差**：
  - `blocked_moves` 召回约 0.79（`abplus_geometry.py:249`）；
  - 便便和坑旁边的起点格会少算，不到一格。
- **不斜穿拐角是保守的**：只会漏掉一些能走的路，不会把走不到的格子当成可达。成功判定用引擎给的坐标，不依赖 d_geo。
- **战斗后尾段里的 COMBAT 步也在 rollout 里**：学习端对每一步都出动作（`gpu_ppo.py:640-690`），尾段的 COMBAT 步一定进 buffer，估计占样本的 40–55%（C39 普通房清房中位 8.9 秒约 67 个决策，对 K=8–16 个目标、每个约 7 个决策）。阶段 1 里它们梯度为 0，但损失按全部样本数 n 归一（`gpu_ppo.py:474`、`:510`），会把 GOTO 的有效学习率、value 和熵权重按份额打折。做法：PPO、value、熵、aux 各项都乘任务掩码，并按本任务的样本数归一；M3 说的“COMBAT 段不进损失”指的就是这个掩码，不是不进 buffer。吞吐和游戏时只按 GOTO 样本计，COMBAT 份额另记。

### 4.8 保持项、学习率与 Adam

- **阶段 1**：共享参数冻结（`requires_grad_(False)`，Adam 会跳过，step 也不增加），所以 L_preserve 恒为 0。新参数 LR 3e-4，余弦退到 3e-5。
- **阶段 2 的学习率**：
  - 共享参数峰值 1e-4（C39 最终的值）；前 5 次更新从 1e-5 线性 warmup，之后余弦退到 1e-5。
  - 新参数 1e-4–3e-4。要分组设学习率，必须覆写 `_update_learning_rate`，因为 SB3 会把所有组设成同一个值（已核实）。
  - 对照：C41 从 1e-4 跳回 1e-3 并载入 Adam，第一轮 kl_full 就是 0.34。
- **Adam**：共享参数按名字从 C39 最终的 `policy.optimizer` 复制 exp_avg、exp_avg_sq、step；新参数用新状态。
- **L_preserve**：
  - 老师取阶段 2 开始时网络的 deepcopy，它在 COMBAT 上等于 C39。这样不走 `load_frozen_policy`，避开它对观测空间的相等检查。
  - 老师 logits 每轮只算一次并缓存，照 `proximal_log_probs` 的做法，约 2.4 MB。
  - KL 只乘 COMBAT 掩码，并按 COMBAT 样本数归一。否则 λ 的实际强度会随任务比例变化。
  - 开销估计：每轮多 3–4 秒，吞吐降约 10%（推测，未实测）。
- **λ 日程**：自适应。每轮测 COMBAT 样本上的累计 KL(π_old‖π_new)，目标 0.05：高于 1.5 倍目标就 λ×1.5，低于目标/1.5 就 λ÷1.5，范围 [0.1, 30]，初值 1.0。大评估通过以后，才放宽目标或让 λ 退到 0。现有的 `distill_coef_end` 只支持按整次预算线性变化（`gpu_ppo.py:246-248`）。
- **KL 门槛的参照（先量再定）**：C39 在性能持平的后期每轮 kl_full 仍有 0.01–0.04（EXPERIMENTS C39 `:2726`），阶段 2 要跑 80–160 轮，累计 KL ≤0.05 可能比“无害漂移”严得多，λ 会一直顶在上限，回滚条件也会频繁误触发。M0 在同一批 COMBAT 输入上量 KL(C39 u700‖u820)、KL(C39 u800‖u820) 和各头的取最大一致率，作为“无害漂移”的量级；自适应 λ 的目标、回滚阈值和离线一致率门槛都按它定。量出来之前，本文的 0.05、0.1、0.9 都算待定。

### 4.9 起点模型（各视角一致）

**推荐 C39 最终**（update-00000820-step-000027000032-final）。理由：
- 评估完整：取最大 121/128；
- 训练分布就是 1×1 房，和第一个里程碑一致；
- 学习率已退到 1e-4，Adam 状态与之匹配；
- 奖励 combat-hp 与阶段 2 的 COMBAT 设置一致。

C41 u50 的问题：
- 没有任何评估记录；
- 存档时学习率约 1e-3，正处在大幅改写期；

- 它在大房间里学到的映射依赖有缺陷的位置编码，改成窗口相对位置以后就失效。

C41 u50 唯一的长处是见过低血量开局，而链里的 B 房会继承 A 房剩下的血量。这一点在 E-CHAIN 里单独量。

C39 的 checkpoint 在第二台上，本机没有。

### 4.10 窗口相对位置与全房间分支

## 6. "大评估"方案

### 6.1 三个套件

**E-COMBAT（战斗能力是否保住）**
- **套件**：C39 的四组，固定开局：满血、1 个炸弹、基础属性。取最大和采样两种模式都跑。
- **种子**：每组 256 个，取一个新的专留区间，不和 2147490000 起、周期评估用的那 32 个重叠。
- **基线**：π_old 同种子跑两遍（A/A），得到噪声底；π_new(COMBAT) 跑一遍。
- **统计**：逐种子配对，胜负用 McNemar，连续量用分层 bootstrap。
- **离线一致性（主要工具）**：拿 π_old 的回放重建输入，在完全相同的输入上逐头算 KL 和取最大一致率。这不受引擎噪声影响。
  - 阶段 1 要求逐位相同；
  - 阶段 2 要求平均 KL ≤ 0.05，移动头和射击头的取最大一致率 ≥ 0.9（建议值）。
- **引擎门槛（建议值）**：
  - 四组合并的胜率非劣效，差距在 2 个百分点以内（单侧 95%）；单组降幅 ≤ 5 个百分点；
  - 清房用时中位 ≤ 基线 × 1.15；
  - 命中率绝对降幅 ≤ 0.05；
  - 每局掉血增加 ≤ 0.3 个半心。
  - 命中率和用时与胜率同等重要：C40 里胜率几乎不变，命中率和用时却大幅变差。
- **不算退化的已知项**：石头 Horf 取最大超时（C39 最终 5/32）、893 号房死亡，这些是 π_old 自己的毛病。

**E-GOTO**
- **题目**：留出房里的（房间、起点 S、目标 G）三元组，直线、绕路、死角各 512 题，另加 256 题"真实清房后的房间"。两种模式。
- **指标**：
  - 成功率；
  - SPL = 成功 × d_geo(S,G) / max(实际路长, d_geo)；
  - 用时与脚本参照之比；
  - 卡住率（longest_stationary > 1 秒）；
  - 尖刺受伤率；
  - 出门率、走错门率；
  - 目标附近的振荡步数。

**E-CHAIN**
- 256 条链，两种模式。
- **指标**：分阶段成功率（A 清房 → 到门 → 进 B → B 清房）、整链成功率、各阶段用时和掉血。
- **对照一**：脚本导航 + π_old 战斗（也就是现行的"导航用规则"）。它与学习版的差距，就是学出来的 GOTO 带来的损失。
- **对照二**：B 房直接用 goto 加载，血量和炸弹与链里进 B 时相同。用来量 option 切换本身有没有干扰。
- **门槛（建议值）**：B 房胜率与对照二的差距 ≤ 5 个百分点，用时 ≤ 对照二 × 1.15；整链成功率 ≥ 对照一 × 0.95。

### 6.2 种子数与统计噪声

- **每组 32 个种子不够**：p=0.94 时标准误是 4.2 个百分点，10 个百分点以下的退化都看不出来。
- **配对 McNemar 的样本量要实测后再定**：A/A 结局全部相同（EXPERIMENTS `:3029`）只说明同一 checkpoint 的不一致率约为 0；阶段 2 的策略变了以后，同种子结局的相关性未知。M0 用 C39 u800 对 u820，在 E-COMBAT 的种子上实测结局不一致率，再按 power.py（`rl/docs/goal_conditioned/power.py`）定每组种子数。参考量级（单侧 5%、功效 80%）：总不一致率 10% 时看出 5 个百分点要约 245 个种子；如果结局近似独立（p≈0.95 时噪声不一致率约 9.5%），5 个百分点约 356 个，3 个百分点约 857 个（推算）。E-CHAIN 的对照二（goto 加载的 B）与链里的 B 敌人随机数不同，不是逐种子配对，门槛改为报告差值和 95% 区间，或按实测方差把链数加够。
- **A/A 必须先做**：同一个 checkpoint 重跑，取最大就有 6–7/64 个种子的轨迹不同，清房用时中位会差 0.3–0.5 秒。
- **主机**：大评估必须在部署了主工作区代码（abp-0.2.12 加本方案改动）和新 libabp_turbo.so 的主机上跑。现在两台都不满足（见 D3）：第二台不换库时，主工作区代码在重置时直接抛 BridgeError（`abplus.py:636-642` 要求三个钩子返回 "111"），不存在“近似配对”这种中间状态。
- **音效状态导致的不确定性（另一个会话 09-30 新发现，未在本方案里复核）**：游戏按 16 个 OpenAL 音源的播放状态决定播不播音效，而虚拟时钟下游戏比音频快约 100 倍，播放状态取决于机器负载，于是同一条轨迹重放会出现不同的隐藏状态（一条 157 步的轨迹重放 12 次得到 7 种状态）。修复是 abp_turbo 的新开关 `ABP_AL_STOPPED=1`，把所有音源都报告为已停止，12/12 一致；默认关闭，目前只编进主机 1 的 Go-Explore 副本。A8 的最终结果（EXPERIMENTS.md A8）：修复只是部分的，回放不一致从 4.7% 降到 1.1%（重试后 0.48%），剩下的都在有 Mulligan 或传送门的房间里，原因未明；而且这个开关明显改变打法：开着它找到的 61 局最佳胜局，关掉它重放只有 39 局完全一致，7 局赢但状态不同，14 局清不了房，1 局死亡。所以训练、评估、示范必须用同一个设置，不能“只在评估开”。用 C39 做基线时，它是在开关关闭的环境里训出来的，开关打开后的成绩要在 M0 里重新量（见 D23）。
- **GOTO 题的可复现性**：GOTO 在桥自己清空并摆放的房间里跑。参照躲子弹场 128/128 完全一致，推测也是精确可复现的，要用 A/A 确认。

### 6.3 成本（估算）

- **E-COMBAT**：每个策略两种模式合计约 7 游戏小时，3 次运行约 21 游戏小时。4 个 CPU worker 约 12× 实时，约 1.8 墙钟小时；不训练时可以加开 worker。
- **E-GOTO**：约 2 游戏小时。
- **E-CHAIN**（含两个对照）：约 8 游戏小时。
