# 宏观层离线工具：AB+ / 忏悔+ 楼层生成器、隐藏房推断、道具先验、规则规划器（2026-09-27）

对应 [MACRO_PLANNING.md](../docs/MACRO_PLANNING.md) 的 P0。全部离线运行，不启动游戏。

**核心**：把 Afterbirth+ v1.06（Linux x64，带函数名）的楼层生成代码逐函数翻译成 Python。
- 给定种子，得到与引擎相同的楼层：网格、房间形状、房间类型和布局、Boss、诅咒，以及每个房间的三个种子。
- 与引擎逐种子、逐房间一致：9,774 个地下室种子的引擎日志，以及 6,000 个引擎整层导出（第 1–8、10、11 层）。范围和局限见下文"验证"。
- 有了它，就能离线生成任意多的楼层当训练数据，也能在已知生成规则下精确推断隐藏房。

**信息边界**（PROJECT_SPEC §3）
- 种子和生成器只用于离线造数据和评估。
- 送给策略的输入只能是玩家看得见的地图，例如 `Floor.visible()` 或规划器里的 `explored_map()`。

## 用法

```python
from isaac_macro.roomconfig import default_room_config
from isaac_macro.level import GameContext, generate_floor
from isaac_macro.run import generate_run
from isaac_macro.floor import Floor
from isaac_macro.secret import secret_posterior

rc = default_room_config()
level = generate_floor(rc, GameContext(), stage=1, stage_type=0, stage_seed=2334308359)
floor = Floor.from_level(level)
print(floor.ascii())                       # S 起点，B Boss，T 宝箱房，$ 商店，s 隐藏房，X 超级隐藏房
run = generate_run(rc, 'SXG6 R8XA', last_stage=8)   # 游戏里显示的种子字符串，或数字种子
post = secret_posterior(floor.visible())   # {格子: 概率}，只用玩家可见的信息
```

- `GameContext` 描述生成时要读的游戏状态：
  - 成就（默认全部解锁）、难度；
  - 玩家的心、钥匙、硬币、饰品、道具；
  - 本局的状态标志（跨层累积，例如已出现过的 Boss 和七宗罪）。
- `debug_start=True`：复现本项目引擎实例的开局方式。实例用 `--set-stage=1 --set-stage-type=0` 启动，走的是 `Game::StartDebug`，所以第一层固定是地下室 I（类型 0），并视为全部解锁。
  - 这也解释了之前 Boss 池探针的疑问："300 局的地下室类型全是 0"。
  - 正常开局走 `Game::Start` → `SetNextStage`，第一层可能是地窖或燃烧地下室。

**网页前端**（`web/`）

```bash
python rl/macro/web/server.py --port 8792
```

- 在仓库根目录下运行，然后打开 http://127.0.0.1:8792/ 。
- 也可以用 `.claude/launch.json` 里的 `abplus-mapgen` 配置启动。
- 后端直接调用上面的生成器，读取本机两个游戏的档案（只读），只在本机运行，游戏数据不外传。
- 页面功能：
  - 选游戏版本：胎衣† v1.06，或忏悔+ v1.9.7.17。忏悔+ 是静态移植，页面上标着"未经游戏验证"，只支持主线路线（见下文"忏悔+ 移植"）；
  - 输入种子（`XXXX XXXX` 或数字），可选开局方式、第 5 章路线、生成到第几层、玩家资源；
  - 每层的缩略图和大地图：可切换显示隐藏房，或显示生成深度。忏悔+ 另有星象房和究极隐藏房；
  - 大地图默认画成游戏里的小地图：房间用游戏的格子贴图（`gfx/ui/minimap1`，每种形状一帧；起始房间画成"当前房间"，要找到才显示的房间画成"没到过"），特殊房间盖上游戏的房间图标（忏悔+ `gfx/ui/minimap_icons`，胎衣† 在 `minimap1` 里），按整数倍放大保持像素清晰。贴图和帧位置由服务端运行时从本机游戏档案里读（`/api/sprites`），仓库里不存游戏图片。勾"文字标签"换回彩色格子加汉字（究极隐藏房标"究"），这个选择存在浏览器里；
  - "玩家视角"：隐去隐藏房，在候选格上显示按规则算出的概率。胎衣† 用 `secret.py`；忏悔+ 用 `rep/secret.py`，多一层究极隐藏房的概率；
  - **联动推断**（玩家视角下）：
    - 服务端把每层的联合后验整张发给页面（每行是隐藏房、超级隐藏房、究极隐藏房的格子和概率；忏悔+ 每层中位数约 100 行）。
    - 点空格子可以记下看到的结果：炸过是空的、开了红房间但没有门通到隐藏房、在这里找到了哪种隐藏房。页面删掉与这些观察不相容的假设再归一化，这就是精确的贝叶斯更新，三种隐藏房的概率一起变。
    - 与已有标记矛盾的结果不会记下，页面会提示（可能是模型没考虑的情况，比如碎卡片带来的第二个隐藏房）。
    - 地图上圈出"下一炸"（炸出隐藏房或超级隐藏房概率最高的墙）和"红钥匙"（在哪个布局门位外开红房间最可能通到究极隐藏房）。
    - 鼠标停在格子上，显示"假如在这里"时其余隐藏房最可能在哪。
    - "红房间没有门通到隐藏房"表示三种隐藏房都不在这格四邻。依据是 J460 的 `Level::MakeRedRoomDoor`（RVA 0x34D010）：新红房间是四面都要求有门的 1×1 布局，它朝每个相邻房间都开门（门位由 `FUN_0074c9e0` 0x34C9E0 给出）；邻居一侧的门只受邻居布局门位限制，最后一个头目房不开。这是静态阅读，没有在游戏里核对；
  - 点击房间：显示布局编号、形状、门、三个房间种子，并画出房间内部布局。布局里有石头、坑、大便等障碍物，刷怪点标出候选实体及权重（名称取自 `entities2.xml`；忏悔+ 的名称按它自带的字符串表换成官方简体中文，例如"裂口尸（Gaper）"）。
- URL 里带着游戏、种子和参数，可以直接收藏或分享链接。

## 验证

**与引擎逐种子一致**〔事实〕
- 数据：本项目 AB+ 实例的 `log.txt`，共 11,048 条地下室 I 记录，去重后 9,774 个种子。其中 154 层有迷宫诅咒，472 层重试过生成。
- 比对内容全部一致：
  - 诅咒；
  - 每一次 `Generate` 的过程：放下的非 1×1 房间形状序列、房间数、循环数、补死路次数、判定结果；
  - "Map Generated in N Loops"；
  - 起始房间的 SpawnRNG 种子。这个种子来自楼层 RNG，它之前的所有抽取都要一致：Boss 选择、各特殊房间的布局与判定、跨层标志等。
- 引擎有 418 次"特殊房间放不下 → 整层重生成"（涉及 403 层），全部复现。这间接验证了 Boss 房和特殊房间在死路上的改形与选择。
- `tests/data/engine_levels_abplus.json` 收了其中 454 层作为回归测试：全部 154 个迷宫层、150 个有放置失败的层、150 个普通层。

**整层逐房间与引擎一致**〔事实，2026-09-26〕
- **怎么测的**：用 [`abplus_probe_floors.py`](../bridge/python/abplus_probe_floors.py) 在远端起一个额外实例（nice 19，约 5 分钟），跑了 600 局。
  - 每局先 `restart`，然后依次用控制台 `stage N`/`Na`/`Nb` 进入各层。
  - 每层用 `Level:GetRooms()` 读出所有房间。
  - `stage` 命令会同步调用 `Level::SetStage` 和 `Level::Init`（`submit_input` 0x12B2D1/0x12B2DD），所以读到的楼层种子就是生成时用的种子。
- **结果**：6,000 层全部一致（`tools/compare_engine_floors.py`）。
  - 113,897/113,897 个房间完全相同，比较的字段是格子、类型、布局编号、子类型、形状，以及三个房间种子；
  - 诅咒 6,000/6,000；
  - 生成时写入的跨层标志 6,000/6,000；
  - 迷宫层 44/44。
- **覆盖范围**：
  - 第 1–8 层的全部三种类型，第 10、11 层的两种类型，每种组合 200 层（地下室 I 普通类型 600 层）。
  - 核对了 6,000 个隐藏房和 6,000 个超级隐藏房的位置。
  - 受资源影响的房间：街机房 958、宝库 348、骰子房 139、献祭房 1,339、挑战房 2,045、卧室 57、图书馆 239、诅咒房 2,494、小头目房 1,196。
- **测试条件**：
  - 调试开局，全部成就解锁；
  - 以撒，带 D6，没有饰品和其他道具；
  - 硬币按局取 0/5/12，钥匙取 0/2，红心取满或少 1 颗。
- 原始数据在 `rl/runs/macro/engine-floors/`（`floors-600.jsonl`，实例的 `log.txt` 也在）。
- 其中 184 层（含全部 44 个迷宫层）收进了 `tests/data/engine_floors_abplus.json.gz` 作为回归测试。

**还没被引擎覆盖的分支**
- **正常开局**：`Game::Start` 从第 0 层走 `SetNextStage`。探针用 `stage` 命令跳层，没有经过这一步；楼层类型规则只核对了反编译。
- **依赖道具或饰品的分支**：
  - 第 7–8 层的银元、血冠；
  - 碎卡片带来的第二个隐藏房；
  - 黑蜡烛、妈妈的盒子；
  - 宝箱房子类型相关的饰品。
- **其他**：未全解锁的存档、困难模式、虚空（第 12 层）。

**未翻译**
- 贪婪模式、???（蓝子宫，第 9 层）、挑战、特殊种子。
- `AllowedDoors`（`precalc_allowed_doors`）。
- 房间内容：敌人和拾取物的生成、道具池抽取。
- （09-27 已补上）档案里经 ISAAC 加扰的存储分块：MiniZ 档案中第一个恰好 0x400 字节的非末尾分块起，后面的分块都原样存储，再与 ISAAC 输出逐字节异或（种子是条目的第二个哈希，ISAAC 的初始结果由一个 PCG 生成器铺出）。房间文件用不到它，PNG 之类不可压缩的文件用它；按这条路径读出的小地图图片全部通过引擎自带的校验和。
- 第 11 层的墓室：它在隐藏房之后才改形，所以隐藏房推断在暗室层会有一点偏差。
  - 另外，墓室的布局来自 0 号房间文件，不能当布局证据用。2026-09-27 之前的版本把它和暗室文件里编号相同的布局混为一谈，暗室层的后验因此出错（596 层里有 38 层，最大差到 0.94）。现在 `FloorRoom.file` 记下布局的来源文件，`LayoutEvidence.known` 只认本层文件的布局。第 1–10 层的结果与改动前逐位相同。

**速度**
- 单核约 5–6 ms/层，含转换成抽象楼层。
- 16 进程约 1,100 层/秒（本机 20 线程）。

## 结果

除特别注明外，以下都在第 1–8 层上统计。
- **生成楼层**：楼层类型和诅咒按整局规则产生；隐藏房、超级隐藏房的真实位置来自生成器本身。
- **引擎楼层**：上面探针读出的 5,200 层（第 1–8 层）。生成器已被证明与引擎逐房间一致，两者本应给出相同的统计。

**隐藏房推断**（`tools/eval_secret.py`；引擎楼层 5,200 层，第 1–8 层）

| 方法 | 第 1 颗命中 | 2 颗内 | 3 颗内 | 平均用弹 |
|---|---:|---:|---:|---:|
| 隐藏房：邻居最多的格子先炸（常见玩法） | 30.4% | 54.7% | 72.6% | 2.82 |
| 隐藏房：先炸"布局有门位却没有门"的墙（玩家经验） | 63.9% | 81.8% | 89.5% | 1.88 |
| 隐藏房：放置规则的精确后验（不看普通房间布局） | 43.0% | 69.8% | 85.5% | 2.16 |
| 隐藏房：**放置规则 + 布局证据** | **88.6%** | **95.6%** | **98.0%** | **1.20** |
| 超级隐藏房：深度先验 | 59.5% | 79.3% | 90.0% | 1.81 |
| 超级隐藏房：**深度先验 + 布局证据** | **76.7%** | **90.0%** | **95.0%** | **1.42** |

在另一批 7,928 个生成楼层上结果一致（`tools/eval_secret.py 1000 2`）：隐藏房 88.9% / 96.6% / 98.7% / 1.17，超级隐藏房 77.6% / 91.0% / 95.9% / 1.39。

- **布局证据**（`LayoutEvidence`、`hidden_posterior`）
  - **来源**：普通房间的布局是在两个隐藏房都放好之后才选的。选布局时要求包含通往隐藏房的门位，并且强烈优先门位恰好等于要求的布局（系数 9.99）。
  - **推论**：某个布局在一面墙上有门位、这面墙外却没有可见的门，要么是一次概率很低的"非精确"抽取，要么墙后就是隐藏房或超级隐藏房。反过来，布局在某面墙上没有门位，就能直接排除墙后的格子。
  - **计算**：按房间库权重精确算出每个房间布局的似然比，与放置规则一起求隐藏房和超级隐藏房位置的联合后验。
  - **与玩家经验的关系**：玩家常说的"对称房间两三面有门、一面是墙时，隐藏房多半在墙后"，就是这条规则的定性版本。
  - **非精确抽取的下限**（09-27）：模型用房间库的初始权重，没有模拟同一层里"选过的布局权重衰减"。
    - 当门位完全吻合的布局权重占比 ×9.99 ≥ 1 时，按初始权重引擎必选吻合的布局，模型会把门位更多的布局判成不可能。
    - 但前面的房间用掉吻合的布局、权重衰减之后，引擎偶尔也会选到门位更多的布局。实测约每 3,000 个这样的房间出现 1 次（AB+ 1/2,629，J460 移植 1/3,176；其他情况下模型预测的比例与实测吻合）。
    - 一旦出现，真实的隐藏房组合就会被判成不可能。现在这条分支至少保留 5×10⁻⁴ 的概率（`secret.NON_EXACT_FLOOR`）。
    - 上表是加了下限之后的结果：引擎楼层上隐藏房第 1 颗命中从 88.0% 升到 88.6%，超级隐藏房从 76.3% 升到 76.7%。
- **前提**：要能认出房间布局，才知道每面墙有没有门位。AB+ 的 13,064 个普通布局里，没有两个布局内容相同而门位不同，所以只要把房间里的障碍物和敌人与房间文件比对，门位就是确定的。桥接还没做这个识别；做之前只能用"放置规则"那一行（平均 2.2 颗）。
- **校准**：预测概率与实际命中频率吻合，例如引擎楼层上 0.856 对 0.857、0.986 对 0.991。
- **只有特殊房间的布局影响放置规则**：黑名单只统计在隐藏房之前放下的房间，即 Boss 房、超级隐藏房和其他特殊房间。普通房间的布局只以"证据"的形式起作用。
- **超级隐藏房的规律**
  - 它总是除 Boss 房外最深的死路，只挨着 1 个普通房间（100%）。
  - 按"深度不小于所有可见死路"筛出的候选平均 5.4 格，真值 100% 在候选中。
  - 先验按两个特征拟合（`tools/fit_super_secret.py`，11,896 层）：相对最深可见死路的深度差，以及相对 Boss 房的深度差（Boss 房先挑最深的死路，比它更深的候选权重只有 0.19）。

**整局一致性检查**（`tools/check_rep_runs.py 400 11 11`）
- 400 个种子 × 两种开局，共 7,924 层（第 1–8、10、11 层），每层约 6.6 ms。
- 没有任何错误，也没有违反这些不变量：每层都有 Boss 房、隐藏房和超级隐藏房，房间不重叠，所有房间都连通。
- 各类房间的出现频率合理：
  - 子宫及以后没有商店和宝箱房；
  - 默认 0 硬币、0 钥匙时没有赌博房和宝库；
  - 星象房约 1%（之前的宝箱房都进过时的基础概率）；
  - 每层都有究极隐藏房。
- 诅咒抽取在 20 万个种子上核对：出诅咒的概率 10.04%，六种各约 1.67%，与规则一致。
- **一个如实复现的引擎怪行为**：七宗罪小头目都出现过之后，小头目段会沿用诅咒房的死路（反编译中的 `local_e8`）。
  - 结果是诅咒房被重复放置，或被普通房间覆盖。
  - 这种情况很罕见，要在游戏里确认。

**隐藏房推断**（`rep/secret.py`；`tools/eval_secret.py 1000 2 --rep`，移植生成的 7,928 层，第 1–8 层）

隐藏房和超级隐藏房的放置规则与 AB+ 相同，只多了"封格"：
- 放好（最后一个）Boss 房后，J460 会封掉它的格子和四邻（VA 0x739A0D）；深牢 II（或迷宫诅咒下的深牢 I）在生成网格时还会封掉起始房间上方的 (6, 5)。隐藏房不会放在被封的格子上。
- 黑名单本来就覆盖了 Boss 房的每一面，所以封格只多排除了 L 形 Boss 房缺角那一格和 (6, 5)。影响很小，但不建模会把真值判成不可能：加非精确下限之前，7,928 层里有 5 层是这样。

新东西是**究极隐藏房**（`GetNewUltraSecretRoom` 0x5AE640，在隐藏房之后放）：
- 它不挨着任何房间或被封的格子。候选格的评分方法和隐藏房一样（Random(5)+10，距离 2 以内有 1、2 个房间时减 6、3）。
- 放好后，距离 2 以内的房间会在朝向它周围空格的每一面加一个门位，也就是红钥匙能开出红房间的位置。普通房间随后才选布局，这些门位也是必需门位。
- 所以一面有门位却没有门的墙，墙后可能是隐藏房、超级隐藏房，也可能是究极隐藏房旁边的红房间空格，三者要放在一起推断。
- 核对：模型推出的普通房间必需门位与生成器的门位逐房间相同（488/488）。约 13% 的普通房间带有红房间门位。

| 方法 | 第 1 次命中 | 2 次内 | 3 次内 | 平均次数 |
|---|---:|---:|---:|---:|
| 隐藏房：邻居最多的格子先炸 | 29.4% | 54.1% | 72.3% | 2.85 |

| 隐藏房：放置规则（不看普通房间布局） | 41.7% | 69.1% | 85.1% | 2.19 |

| 隐藏房：**规则 + 布局证据，含究极隐藏房** | **88.4%** | **96.4%** | **98.5%** | **1.18** |

- 究极隐藏房不是炸出来的，要用红钥匙开红房间，所以这几行的"次数"是按概率顺序猜格子的次数。
- "已找到 / 已知"几行是把联合后验按真实位置条件化，网页上的标记做的就是这件事。
- 两种后验都校准得很好，例如隐藏房 0.856 对 0.863，究极隐藏房 0.854 对 0.870。

**两条玩家经验的量化**（同一批 7,928 层；`eval_secret.py --rep` 末尾会打印）
- **"红隐大多生成在四周有好几个房间的地方"**：真实红隐距离 2 以内有 ≥2 个房间格的占 92.5%（≥3 的占 45.7%），而所有合法格子里只有 29.8%。这是放置规则的直接结果：候选格按距离 2 以内被占的格子数打分，只有 1 格的减 6、2 格的减 3，3 格以上不减。
- **"红隐概率高了，隐藏房的后验会下降，甚至排除某些候选"**：红隐离隐藏房、超级隐藏房的曼哈顿距离都至少 3。挨着它或只隔一格的格子都会落选，因为这两种房间每一面的门位目标都在红隐的黑名单里。红隐还会给附近房间加红房间门位。
  - 和不管红隐的 AB+ 模型相比，485 层（6.1%）里有原本 ≥10% 的隐藏房候选被压到 1% 以下，一次也没有压错。
  - 1,248 层里有候选的概率减半，其中 93 次减半的正好是真正的隐藏房。
- 反过来也成立：找到隐藏房后，红隐第一猜从 74.5% 升到 77.5%；知道红隐位置时，隐藏房第 1 颗命中从 88.4% 升到 91.7%。
- 超级隐藏房先验在忏悔+ 楼层上重新拟合（`tools/fit_super_secret.py 1500 1 --rep`，11,896 层）。放置方法相同，权重与 AB+ 的差别在噪声以内。
- 这些数字相对于未经验证的移植；与游戏核对后才能当成游戏里的命中率。
