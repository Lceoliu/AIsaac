# AB+ 实验结论与关键数据

整理：2026-10-21。本文是历史实验账本，不是远端任务状态页。保留实验条件、关键结果、负结果和评估口径；逐次进度播报、过期 ETA、完整启动参数及排障流水不再重复维护。

## 阅读口径

- 平均过层数不是整局通关率；32/128 种子跟踪不能替代 512 种子正式比较。不同任务、种子、停滞规则、起始分布不能直接横比。
- 游戏小时 = 决策数 × 每决策帧数 ÷ 30 ÷ 3600；实时倍率 = 决策数/墙钟秒 × 每决策帧数 ÷ 30。C38 及以前通常每决策 2 帧，C39 起通常 4 帧，以运行配置为准。
- 可恢复实验以运行目录内的 `config.json`、`progress.csv`、`episodes.jsonl`、评估 `summary.json/results.jsonl` 和检查点为证据。远端旧路径只表示当时位置，不保证现在仍可访问。
- 以下“冒烟通过”只证明所测路径能运行；吞吐结果只适用于当时硬件、负载及完整开关组合。旧记录中的待测项不自动升级为完成。
- 原始文本可通过 Git 历史回溯；本轮未删除训练原始日志、评估结果或模型权重。

### B19-pre HPC 节点上线：吞吐基准、配额、克隆体死亡

- `cat /sys/fs/cgroup/cpu.max` = **160 核配额**（不是 224）：128 worker 塌到 175×（collect 46 秒），96 worker 同步也塌（collect 12–23 秒）；64 worker 可用。

**实验方法**
opus 子代理实现，我复核 GraphActor 的设备侧写入与 rollout 设备池；提交 `7c6a04b`。(1) 时间侧数据（每层 K/V bf16、s、o、房间 token 来源）放在每份 rollout 的设备张量池里（`t_assign/t_dest/t_free/t_grow`，池按需增长、增长前排空在飞的调用），actor 的图输出用 `index_copy_` 直接写进 rollout 行（`submit(tdest=)`、`_t_store`），学习器在设备上 gather（`temporal_inputs` 只建索引），`carry` 设备内拷贝上下文；每步跨总线 8 B 进 + 16 B 出（B30 约 5.6 KB 来回）；两份 rollout 约 570 MB 显存（各含自己的 255 步上下文）。(2) 历史 token 作为融合注意力里的一个普通 token（顺序 … 道具、历史、全局），门 g2 只乘它的值向量，无上一步时屏蔽它的 key（永远不用门值屏蔽，保证 g2 在 0 处有梯度）；`_hist/_hist_update` 及 packed/bucket 特例全部删除。(3) `TemporalAttention.room_table`：每个 epoch 对整份 rollout 的房间按 (worker, 局) 因果算一次每层 K/V，`sequence` 的块前房间从表里取，块内房间照旧有梯度。
- **测试**：`test_temporal_smoke.py` 27 项全过（PC 与 HPC160 H20，含 GraphActor）：门零对关闭不再逐位——小模型 logit 最大差 0.139（logit 量级 4.8，2.9%）、C95 尺寸的 resume 0.103（2.3%），动作全同；逐步 actor 对一次性学习器 1.2e-6（容差收紧到 1e-5）；bf16 rollout 对 bf16 actor 6.8e-4；门零时 Q 和 hist_kind 也通过 key 得到梯度。CPU 基准：学习器块开销比 B30 ×1.45 → **×1.06–1.19**（+ 每 epoch 房间表 3–4 ms）；actor eager 无明显变化。
- **冒烟**（HPC160 `ws9`，8 worker、C95 u65000 续训，与 C95 同节点）：无加速——0 Traceback，update **2.3–3.1 s**（B30 3.2–4.1，B24 1.7），infer 10.0 ms（B30 9.4）；加速——0 Traceback，update 2.4–3.5 s，**infer 4.7–4.95 ms（B30 + 加速 3.1）**，首次更新 KL 0.029（门零偏差所致），之后 0.01–0.028。编译时间都算在 8 分钟的冒烟里，infer 的差异不能定论。
**结论**：学习器的目标达到（每次更新比 B30 省 25–30%）；actor 在加速标志下反而比 B30 慢 1.6 ms 的原因待查（候选：多一个 token 让记录落到更大的实体分桶、`_t_store` 的 index_copy、编译缓存未命中），由 C96 的 64 worker 真实数字判断。C96 改用 B31 启动（ws9 已切到 7c6a04b）。

### B36 lane 服务异步化

- **代码**（提交 `a736edf` + `69000df`，opus 子代理）：`isaac_bridge/tok_lanes.py` 的 `LaneService`——每轮循环无阻塞地读所有等待中的 lane 请求，最老请求满 `--cf-lane-wait` 2 ms 或 `--cf-lane-quiet` 0.5 ms 内无新请求就开一次调用（按行分桶取最小合适的图），**只提交不等待**（状态复制与读出都在 lane 流上以事件结束，actor 继续服务 worker，事件完成再回复），同一时刻最多一个 lane 调用在飞、不跨权重更新；每个请求的随机数按（序号, lane）取键，答复不随同批的其他 lane 变化；陈旧答复的回显改为取请求时的序号（修了一个被杀子进程的答复可能被下一个子进程接受的 bug）。新列 `v2_lane_fly_s` / `v2_lane_held_s` / `v2_lane_eager`。无检查点/配置变化。

### B38 多 GPU / 多进程吞吐：五步工程实验合并结论

- 两卡同进程/双线程重叠只快约 16%；共享 Python GIL 限制学习器速度。改为 learner 独立进程后，无搜索配置 **1,515–1,539×**；不能把它当完整 CF 配方速度。

- `--learner-fast 2` 减少学习器固定开销；它与 actor 进程拆分是工程维度，不等同于增加训练样本或改变奖励。
- 第二个 actor 在无搜索配置下几乎无收益：**1,902 vs 1,912×**，瓶颈仍为 learner。完整配置、64 workers 的四卡历史测试为 **1,775×**，collect **2.43 s**、update **2.27 s**；相对两卡进程模式 **1,415–1,560×** 约快 15%。
- 结论仅限当时模型、硬件和开关：多 GPU 不自动提速，必须看采样与更新的重叠瓶颈；旧吞吐不能替代新记忆模型的测速。

### A30 宝箱房道具值不值、价值头知不知道：反事实双支诊断
