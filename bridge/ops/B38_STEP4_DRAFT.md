### B38 第四步：压学习器每一份的固定开销（`--learner-fast 2`）（2026-10-17，代码完成，未上线）

**实验目的**

第三步测出学习器每一份（一次前向 + 反向）有 50–70 ms 与行数几乎无关的固定开销，双卡按行切分没有用。第四步在**不改优化**（同样的小批 4,096 / micro 4,096、同样的步数、同样的梯度，只允许浮点误差）的前提下把 update 从约 2.8 s 压到 ≤ 2.2 s：先剖析每步的时间去向，再按协调者的顺序试 CUDA Graph、torch.compile、去主机同步、重算阶段。

**实验方法**

- **分支** `b38-learner-fast`（从 abplus-training `c3a9627` 开，第三步的 3a 代码不在里面）；opus 子代理实现。
- **测量工具**（`30a1430` 起）：把第三步的回放台架（`abplus_b38_replay.py`，不带 actor、游戏，把存下的 C99 规模作业——32,768 个决策——反复交给一个学习器进程）移到单进程版；`ISAAC_RL_B38_TORCHPROF=<目录>` 让学习器进程的第 k 次更新在 torch profiler 下跑（算子表 + Chrome trace；每一份标出 `b38:part_plan / forward / loss / backward / stats`、`b38:clip_opt`、`b38:recompute` 区段）；`ISAAC_RL_B38_SYNCDEBUG_AT=k` 列出一次更新里每一处主机同步及其代码行；`ops/hpc_b38_step4.sh`（回放）。全部在主机 A 的 GPU 2、3，不带搜索，起点 `segment1-final.pt`。
- **实现**（`--learner-fast 2`，默认 0 / C99 用的 1 都不变；`bd259fe` 1–3，`b566a18` 4，`c2e306e` 测试；`f0bd123` 的 `--learner-compile` 是试验，留着但不建议用）：
  1. 更新开始时的重算（`--decoupled 1` / `--recompute-values`）改走 B18 快路径的主机计划：每 4,096 行一块按 PPO 份的做法建计划（注意力按长度分桶、只算真 token、CNN 只算不同的格子），记录先拷进固定内存再一次异步上传（原来是 690 MB 的分页内存同步拷贝），并保留记录的字节（`fast_plan_counts` / `fast_plan_rows`）。
  2. 重算之后的 PPO 份也从这些字节里取（B18 的按字节 gather；原来有重算时退回逐字段 gather，每份约 20 次 gather）；值逐位相同。
  3. 物品 token 数按字段取（`row_fields`），不再把整条 20.8 KB 的记录复制一遍（每次更新 690 MB 的主机拷贝）。
  4. CNN 的"不同格子"批量补到 64 的倍数（用第一个格子的副本补，结果不取回）：卷积只见到少数几种批大小，cuDNN 的执行计划可以复用（原来每次调用约 0.6 ms 的 CPU 花在选算法上）。
- **单元测试** `tests/test_learner_fast2_smoke.py`（CPU 与 GPU 各一遍，8 项全过）：(a) 新重算的 logits、value、value_global、log-prob 与原路径相差 ≤ 6e-7；(b) 从字节建的 PPO 批与逐字段 gather 逐位相同；(c) CNN 补齐前后的输出相同（CPU 0、GPU 6e-7），梯度的相对差 CPU 1e-6、GPU 6.8e-4（TF32 卷积在不同批大小下选了不同算法）；(d) 按字段取的物品数与整条记录的相同。其余 11 个冒烟测试（含 `test_learner_device_smoke`）在最终代码上全过。整次更新的权重不做逐位比较：第三步已测出 GPU 上同一配置两次回放的更新之间 cos 只有 0.865（原子加法的顺序 + Adam 对近零梯度的放大），只能在前向与梯度层面验证。

**实验结果**

- **剖析**（一次 C99 规模的更新，原路径，profiler 下 3.4 s；每步 = 一份）：

  | 区段 | 每份墙钟 ms | 区段内 GPU 忙 |
  |---|---:|---:|
  | 份的准备（逐字段 gather、主机计划、上传） | 7.5 | 8% |
  | 前向 | 30.7 | 45% |
  | 损失 | 2.0 | 20% |
  | 反向（autograd 线程发 kernel） | 26.5 | 53% |
  | 裁剪 + fused Adam | 5.4 | 14% |
  | 重算（8 块，整段） | 283 | 93% |

  - 整次更新 GPU 只忙 44%（1.74 s / 3.96 s），每步约 2,270 次 kernel 发射（每次 5–6 µs 的 `cudaLaunchKernel` 加上调度器开销）；前向和反向都是**主机线程限速**（GPU 一半时间空着）。
  - 最贵的几项：cuDNN 卷积每次调用 0.56 ms CPU（前向 273 次、反向 210 次，批大小每份都不同，每次重新查算法：`cudaFuncGetAttributes` 1.1 万次）；重算前 690 MB 的分页内存同步上传和逐字段 gather；有重算时 PPO 份退回逐字段 gather；`item_count` 复制整条记录。
  - 主机同步每步约 3 次（`used_entities` 的 `.max()`、重算里的 `nonzero`、几处 `torch.from_numpy(...).to()`），但主机本来就是瓶颈，GPU 在同步点通常已经空了，不是主要成本，没有专门去掉。
- **回放台架**（同一个作业，各 8 次的中位数；同一时段的原路径作对照，因为主机 A 的负载在 60–80 之间波动，原路径在不同时段是 2.77–3.12 s）：

  | 配置 | update 秒 | 重算 + PPO + opt | 学习器显存 GB |
  |---|---:|---|---:|
  | 原路径（`--learner-fast 1`） | 2.94（另一时段 3.12、2.77） | 0.52 + 2.21 + 0.13 | 6.8 |
  | torch.compile（default，动态形状） | 2.93（首次编译 480 s） | 0.52 + 2.14 + 0.14 | 6.4 |
  | fast 2，只有 1–3 | 2.36 | 0.27 + 1.89 + 0.13 | 7.5 |
  | **fast 2，1–4（CNN 补到 64）** | **2.11** | 0.27 + 1.61 + 0.13 | 7.5 |
  | fast 2，CNN 补到 128 | 2.14 | 0.27 + 1.65 + 0.13 | 7.6 |
  | fast 2 + cuDNN benchmark | 2.24 | 0.26 + 1.78 + 0.12 | 7.5 |

- **真实训练器**（无搜索，`segment1-final.pt` 续 60 次更新，中位数；p = g + `--learner-fast 2`）：

  | 运行 | worker | 更新数 | × 实时 | collect 秒 | update 秒（重算 + PPO + opt） | wait_learner 秒 | 推理 ms | clip_frac | kl | 显存 GB（学习器 / actor） | 训练器核数（actor + 学习器） |
  |---|---:|---:|---:|---:|---|---:|---:|---:|---:|---|---|
  | a 单卡同步（第二步 tput3） | 64 | 61 | 1,011 | 1.85 | 2.47 | — | 2.40 | 0.128 | 0.014 | 9.0（同卡） | 1.8 |
  | g 第二步 | 64 | 61 | 1,625 | 1.81 | 2.67（0.58 + 1.87 + 0.12） | 0.86 | 2.36 | 0.134 | 0.036 | 7.4 / 1.15 | 0.69 + 1.91 |
  | g 第二步 | 48 | 46（被负载守护停下） | 1,685 | 2.32 | 2.57（0.56 + 1.81 + 0.11） | 0.26 | 2.33 | 0.122 | 0.032 | 8.8 / 1.09 | 0.90 + 2.08 |
  | **p = g + fast 2** | 48 | 61 | **1,902** | 2.30 | **1.94**（0.28 + 1.47 + 0.10） | **0** | 2.33 | 0.117 | 0.028 | 8.6 / 1.06 | 1.0 + 2.0 |

  - 冒烟（8 worker、1.5 游戏小时、从零）：p 0 个 Traceback，304×，kl 0.007、ev 0.50（g 第二步 293×、0.004、0.65）。
  - 真实运行里 update 从 2.57–2.67 s 降到 **1.94 s（−25%）**，低于 2.2 s 的目标；p 在 48 个 worker 时已经是采集限速（collect 2.30 s > update 1.94 s，wait_learner 0），比同 worker 数的 g 快 13%。
  - 64 个 worker 的 p 跑不成：主机 A 现在 C99 自己的负载约 65–80（1,590×，worker 空等少了），64 个 worker 的启动尖峰两次超过 90 被守护停下（g 的 64 worker 那次是在第 61 次更新时被停的，数据完整）。按 g 的 64 worker collect 1.81 s 估算，p 在 64 个 worker 时周期约 max(1.81, 1.94) ≈ 1.95 s → **约 2,200×**（未测）。
- **没做 / 不可行的**：
  - CUDA Graph：学习器每一份的形状都在变（份的行数、实体 token 数、真 token 数、注意力分桶的个数和宽度、温度块里的房间数），按形状捕获不可行；要用图就得把学习器改成固定形状的补齐布局（放弃 B18 的大部分省算），是另一个工程。
  - torch.compile（动态形状）：首次编译 480 s，重算路径在 `nonzero` 处断图，步长 / 尺寸相同性守卫引起多次重编译；稳定后 2.93 s，没有收益。
  - cuDNN benchmark：更慢（每种新形状都要试算法）。
- **上限与原因**：fast 2 之后每步约 49 ms（PPO 1.47–1.61 s / 30 步），主要是前向和反向的算子调度（每步两千多个 kernel，主机线程一半时间在发射）；GPU 本身每步约需 40 ms 左右。再往下需要减少 kernel 个数（融合 / 编译成功且不断图）或固定形状后用 CUDA Graph。
- **对 C99 全标志的意义**（估计）：C99 现在 collect 2.8 s、update 2.7 s；fast 2 后 update 约 2.0 s，周期变成采集限速（约 2.8 s），只多几个百分点；要到 2,000× 还需要第二个 actor 进程（3b）把 collect 降下来。fast 2 是 3b 的前提：没有它，3b 之后周期会卡在学习器的 2.7 s。
- **没测**：64 worker 的 p（负载上限）；带搜索 / lane / 教师记录的 fast 2（主机 A 上不允许）；GRU 记忆模型的 fast 2（单元测试覆盖了带 GRU 的温度模型的前向，真实训练没跑）。
