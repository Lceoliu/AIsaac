### B38 第三步：学习器跨两块卡（3a）与第二个 actor（3b）的评估（2026-10-17，3a 代码完成但不建议用，3b 未实现）

**实验目的**

用户的目标是**一个任务** 2,000× 以上、允许用 4 块卡。第二步上线后 C99（全标志、进程模式）约 1,415–1,515×：collect 2.7–2.9 s、update 2.8–3.1 s，两边差不多一样长。3a：学习器拆成每卡一个进程，每个小批按行分给各进程、梯度求和（同样的有效批、同样的优化器状态），目标 update 从约 3.0 s 降到约 1.7 s。3b：第二块 actor 卡，二选一：(i) 同一进程里第二套 GraphActor / lane；(ii) 第二个 actor 进程管一半 worker。先测再决定。

**实验方法**

- **合并**：`b38-learner-device` 快进到 abplus-training（`4a0b93d`，含合并提交 `b1287fc`），之后的提交都在它上面。
- **3a 代码**（`125f96d` 主体，`35df61e` 用 /dev/shm 文件做会合点；opus 子代理实现）：
  - `--learner-device cuda:1,cuda:2`（列表，需要 `--learner-process 1`、`--teach-merge 1`，各卡互不相同且不是 actor 的卡）：每张卡一个学习器进程（rank），都收到同一个作业、各自把 rollout 镜像到自己的卡上（第二步的 `hand_off`）。
  - 每个小批切成至少每 rank 一份（`micro // ranks`，温度模型按整块），第 i 份归 rank `i % ranks`；每份的损失本来就带着它在整个小批里的份额（`w`），所以各 rank 梯度**求和**就是整个小批的梯度（`allreduce_grads`：各 rank 先在主机上用 gloo 商定哪些参数有梯度——只有某个 rank 碰到的参数（例如老师记录只在最后一份里，危险头）别的 rank 补零，谁都没碰到的保持 None，和单进程时一样被 Adam 跳过；再一次 NCCL 平铺 all-reduce）；随后各 rank 用同一梯度做同样的裁剪和 fused Adam，权重保持一致（每次更新检查一次：`ddp_spread` = 各 rank 权重校验和的极差）。
  - 价值 / log-prob 重算按 4,096 行的块轮流分给各 rank，其他块填零，求和合并；小批的排列由 rank 0 广播；统计量（pg、vf、熵、kl 等）在 `fresh` 前求和。rank 0 发布权重、存检查点、写 progress.csv；其他 rank 在 `fresh` 后直接返回。
  - 故障：任一 rank 出错都通过结果队列报给训练器；训练器看到错误后最多等 60 s 让 rank 0 存 `last.pt`，然后结束剩下的进程。
  - 测试辅助：`ISAAC_RL_B38_SHARED_GPU=1`（允许一个 rank 和 actor 共卡，只用于卡不够时的功能测试，B13 风险）、`ISAAC_RL_B38_DUMP`（把某个作业存盘）、`abplus_b38_replay.py`（不带 actor 和游戏，把存盘的作业反复交给 1 个或 2 个学习器 rank，计时并比较权重）、`ops/b38_compare.py`。
- **测试**：`tests/test_learner_device_smoke.py` 新增 (f)：两个 gloo rank 各算一份的梯度经 `allreduce_grads` 求和 == 单进程两份累加，逐位相同（含只有一个 rank 碰到的危险头参数），Adam 之后两 rank 与单进程参数逐位相同；全文件 12 项在主机 A（GPU 2、3）全过。
- **主机限制**：只能用 GPU 2、3（C99 占 0、1）。3a 的端到端运行需要 3 块卡（actor + 2 个学习器），3a+3b 需要 4 块，都跑不了；因此：功能冒烟让 rank 1 与 actor 共用 GPU 2（`ISAAC_RL_B38_SHARED_GPU=1`，8 worker，无搜索）；速度用回放：从一次 64 worker、无搜索的 g 运行里存下第 8 个作业（32,768 个决策、1.04 GB），再在 GPU 2、3 上不带 actor 地回放 8 次（同一起点 `segment1-final.pt`）。全部不带搜索，负载守护 90。
- **3b 的依据**：C99 现在的 progress.csv 最后 60 行（全标志、进程模式）里 actor 主线程的时间分解（`p_*`、`v2_lane_s`）和 worker 的空等（`w_wait`、`idle_share`）。

**实验结果**

- **第二步的端到端参考**（64 worker、无搜索，第二步的 tput3，第 9–61 次更新中位数）：

  | 变体 | × 实时 | collect 秒 | update 秒 | wait_learner 秒 | 推理 ms | clip_frac | kl | 显存 GB（学习器 / actor） | 训练器核数 |
  |---|---:|---:|---:|---:|---:|---:|---:|---|---|
  | a 单卡同步 | 1,011 | 1.85 | 2.47 | — | 2.40 | 0.128 | 0.014 | 9.0（同卡） | 1.8 |
  | b 双卡线程重叠 | 1,200 | 2.24 | 3.62 | 1.41 | 2.80 | 0.129 | 0.035 | 7.95 / 1.07 | 2.4 |
  | g 双卡进程重叠（第二步） | 1,539 | 1.82 | 2.82 | 0.99 | 2.39 | 0.130 | 0.033 | 7.0 / 1.15 | 0.65 + 2.1 |
  | 3a 双学习器卡 | 无法端到端测（需要 3 块卡），见下面的回放 | | | | | | | | |
  | 3a + 3b | 未实现（见下） | | | | | | | | |

- **3a 功能**：冒烟（rank 0 在 GPU 3、rank 1 与 actor 共用 GPU 2）0 个 Traceback，5 次更新 `ddp_spread` 全是 0（两个 rank 的权重一直相同），kl 0.0006–0.015；故障注入（rank 1 在第 3 次更新前抛异常）：训练器以该错误结束，rank 0 存了 `last.pt`（rank 1 退出时它在 gloo 上的等待随之报错），没有遗留进程。
- **3a 速度（回放同一个作业，每种 8 次的中位数）**：

  | 学习器 | 小批 / micro | update 秒 | 重算 | PPO | opt | 每 rank 显存 GB |
  |---|---|---:|---:|---:|---:|---|
  | 1 rank（GPU 2） | 4096 / 4096 | **2.77** | 0.55 | 2.03 | 0.12 | 6.8 |
  | 1 rank（GPU 3） | 4096 / 4096 | 2.81 | 0.55 | 2.06 | 0.14 | 6.8 |
  | **2 rank** | 4096 / 4096（每 rank 2,048 行） | **3.18** | 0.44 | 2.31 | 0.37 | 4.7 / 4.9 |
  | 1 rank | 4096 / 2048（每步两份） | 5.06 | 0.55 | 4.26 | 0.16 | 4.7 |
  | 1 rank | 8192 / 8192（12 步而不是 24） | **2.21** | 0.55 | 1.43 | 0.08 | 11.4 |
  | 2 rank | 8192 / 8192（每 rank 4,096 行） | 2.05 | 0.42 | 1.30 | 0.23 | 8.2 / 8.2 |

  - 1 rank 的回放（2.77 s）与 g 的真实运行（2.82 s）一致，回放有代表性。
  - **两个 rank 反而更慢**（3.18 对 2.77 s）。原因：学习器每一份（一次前向 + 反向）的时间几乎与行数无关——同样 4,096 行的小批切成两份，单进程用时从 2.03 s 翻到 4.26 s；8,192 行一份每步只比 4,096 行多约 40%。也就是说每一份有约 50–70 ms 的固定开销（kernel 发射 / 主机线程，B18 已知学习器受主机线程限制，学习器卡利用率约 40%），而两个 rank 每步仍各要做一份完整的前向反向，固定开销一点没少，还多了每步的梯度归约和两 rank 互等（opt 0.12 → 0.37 s）。重算部分有一点收益（0.55 → 0.44 s）。
  - **权重一致性**：单元测试逐位；真实训练器 `ddp_spread` 恒为 0；回放一次更新后比较更新量：两次完全相同的 1 rank 回放之间 cos 0.865（相对距离 0.52），2 rank 与 1 rank 之间 cos 0.82–0.86（0.52–0.59），在 GPU 自身的不确定性之内。另一个发现：带 `--learner-fast 1` 的学习器一次更新在同一块卡上本身就不可复现到这个程度（原子操作的求和顺序加上 Adam 对近零梯度的放大），这不影响训练，但以后"逐位相同"只能在 CPU 或单步上检验。
  - 结论：**按行切的 3a 在这台机器上不会降低 update**，不建议上线（代码保留、默认关闭）。真正能缩短 update 的是更少、更大的步：小批 8,192（每次更新 12 步而不是 24）单卡就到 2.21 s（-20%，clip_frac 0.09 对 0.18：每次更新的步数减半，学习动力学会变，需要学习对照，属于用户的决定），两卡再到 2.05 s；或者降低每一份的固定开销（学习器的 CUDA Graph / 编译：发射开销是主体，这是一个独立的工程）。
- **3b 评估**（C99 全标志、进程模式，最后 60 次更新中位数：1,514×，collect 2.84 s，update 2.78 s）：
  - actor 主线程在 collect 里几乎没有空闲：调用 1.16 s（1,143 次，提交与取结果）、记账 0.36 s、写 rollout 0.21 s、轮询 0.19 s、回复 0.13 s、lane 服务 0.70 s，合计约 2.75 s / 2.84 s。worker 每周期一半时间在等（`idle_share` 0.52：每个 worker 每周期跑 1.0 s、编码 0.36 s、等 1.5 s）。推理延迟 3.9 ms 在两个槽里与主机工作重叠。collect 是**actor 进程的主机线程**限速，不是 GPU、也不是 worker 的 CPU。
  - (i) 同一进程里加第二块 actor 卡：主线程的主机工作不变（甚至更多），**不可行**。
  - (ii) 第二个 actor 进程管一半 worker：每个进程的主机工作减半，collect 预计可降到约 1.5 s——**方向成立**。但现在 update（2.78 s）和 collect 一样长，只降 collect 的话周期仍是 2.78 s，约 1,570×（+4%）；只有在学习器也变快以后它才有用。它的改动面很大（两个采样器写同一份共享 rollout 的不同 worker 行、两套设备行池在学习器镜像里拼接和重编号、两个 actor 的权重同步与重叠语义、两边的教师记录和统计），而且在只有 GPU 2、3 的条件下无法测吞吐（需要 2 张 actor 卡 + 至少 1 张学习器卡）。**本步不实现**。
- **到 2,000× 的路线**（估计）：先把学习器降到 ≤ 2.2 s（小批 8,192 是已测的最便宜办法，单卡 2.21 s；或学习器 CUDA Graph），这时周期由 collect（2.84 s）决定，约 1,540×；再做 3b(ii) 把 collect 降到约 1.5 s，周期约 2.2 s → 32,768 × 4 / 30 / 2.2 ≈ **2,000×**。CPU：C99 现在约 55 个负载，3b 之后 worker 不再空等一半，worker 的 CPU 约增加一倍，估计 75–90 核，在 128 核配额内但接近用户给的 90。
- **没测**：3a 的端到端吞吐（需要 3 块卡）；3a 与搜索 / lane / 教师记录同开（主机 A 上不允许）；3a 下 rank 在 NCCL 集合操作里卡住时的退出（训练器等 60 s 后结束进程，不保证 `last.pt`）；GRU 记忆模型的 3a。
