### B38 第一步：学习器放到第二块 GPU（`--learner-device`）并与采样重叠（2026-10-17，代码完成，未上线）

**实验目的**

用户 10-17：一台主机只跑一个任务，把**一个任务**的吞吐推到极限（2,000× 以上），允许多卡。C99 在主机 A 一块 H20 上同步训练：一个周期 = collect 2.7 s + update 2.9–3.1 s，约 760×（64 worker）。B11 的 `--overlap` 在单卡上让 actor 推理变慢约一倍（GPU 争用），B13 共卡重叠时还有非法内存访问崩溃，所以之后一直"一卡一训练器、不重叠"。设想：actor（推理、lane、快照、rollout）留在 GPU A，学习器去 GPU B，用 `--overlap` 让第 k 次更新和第 k+1 次采集同时进行，周期从 collect + update 变成 max(collect, update)，预期约 1,500×。

**实验方法**

- **代码**（分支 `b38-learner-device`：`398a525` 代码与测试，`7398d3a` / `0cfa045` 测试脚本；opus 子代理实现，未合入 abplus-training）：
  - `train_tok.py --learner-device cuda:N`（默认空 = 与 actor 同卡，代码路径与之前相同）：`learner_model`、Adam、choice 优化器、`learn()` 里建的每个张量（批、teacher / teacher-v2 环、温度房间表、`--resume` / `--init` 的加载）都在学习器的卡上；学习器线程 `set_device` 后再设自己的流。
  - **交接**：actor 流同步后，把 rollout 已用的时间行（K/V 与 o；s 学习器不读）在一对专用流上异步拷到学习器卡上的常驻镜像（`mirror_temporal` / `hand_off`，学习器在事件上等待），actor 立刻继续写另一份 rollout；一份镜像够用，因为下一次交接一定在读它的那次更新同步完自己的流之后。每行 5,120 字节（K/V 4 层 × 2 × 256 × bf16 + o 256 × fp32）；64 worker、rollout 32,768 时每次更新 **248 MiB**（实测 `handoff_mb`），走 NVLink（NV18），主机侧发起耗时 0.25–0.6 ms。
  - **换权重**：学习器的参数和缓冲按字节拼成一块（学习器卡上的专用流，先等学习器流），一次对等拷贝到 actor 卡，再 `_foreach_copy_` 写回 actor 参数（原地，CUDA 图照旧读它们）；26.9 MiB，`take_weights` 含同步 7.8–9.5 ms。
  - progress.csv 新列（仅双卡时）：`gpu_reserved_gb_actor`、`handoff_mb`、`handoff_s`、`take_weights_s`；`gpu_reserved_gb` 双卡时是学习器卡。`collect_s` / `update_s` / `wait_learner_s` 含义不变。
- **测试**：新 `tests/test_learner_device_smoke.py` 7 项（镜像上的学习器分块前向 == 原 rollout 逐位，未拷贝的行灌 NaN 也不被读到；镜像在不同池大小间重分配；cuda:0 → cuda:1 交接后行逐位相同、房间表相同；`move_weights` 两次逐位相同且原地；逐张量回退相同），原 10 个冒烟测试在主机 A（GPU 1、2）全过。
- **测试沙箱**：主机 A `ws14`（`mk_ws14.sh`，引擎与 Lua 从 ws9 复制，Xvfb :95），只用 GPU 1、2（`CUDA_VISIBLE_DEVICES=1,2`），C99 在 GPU 0 照常。脚本 `hpc_b38.sh`，汇总 `b38_summary.py`。变体：a 单卡同步（= C99）；b 双卡 + `--overlap --decoupled 1`；c 双卡同步；d 单卡 + `--overlap --decoupled 1`；e 双卡 + `--overlap`、普通比率、不重算（`--recompute-values off`）；f 同 b、`--switch-interval 0.005`。
- **冒烟**：C99 配方从零，8 worker，1.5 游戏小时（5 次更新），a / b / c。
- **吞吐**：64 worker，`--rollout 32768 --minibatch 4096 --micro 4096 --learner-fast 1` + B29 actor 标志，从 C99 的 `segment1-final.pt` `--resume` 到 `ws14/runs/` 新目录，每个 73 游戏小时（60 次更新），取第 9–61 次的中位数。第一次用 C99 全部标志（含教师与反事实搜索）只跑了 a 就出了下文的负载事故；之后的六个变体都**去掉了搜索**（无 `--teacher`、`--cf 0`，其余同 C99），并加了负载守护（1 分钟负载连续 30 秒高于 85 就 SIGINT）。

**实验结果**

- **冒烟**（0 个 Traceback；5 次更新的中位数，从零）：a 182×、kl 0.0037、ev 0.31；b 297×、kl 0.0075、ev 0.25；c 184×、kl 0.0011、ev 0.09（ev 在前几次更新里从 0 往上走，三者同量级）。
- **吞吐**（64 worker、无搜索，主机 A 负载 46–57，含 C99 约 31；0 个 Traceback）：

  | 变体 | × 实时 | collect 秒 | update 秒（重算 + PPO + opt） | wait_learner 秒 | 周期 秒 | actor 一次调用 ms | worker 空等 | clip_frac | kl | 显存 GB（学习器 / actor） |
  |---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---|
  | a 单卡同步 | 1,051 | 1.86 | 2.32（0 + 1.99 + 0.11） | — | 4.16 | 2.44 | 0.76 | 0.133 | 0.014 | 8.5（同一卡） |
  | b 双卡重叠 + 解耦 | **1,216** | 2.18 | 3.57（0.60 + 2.72 + 0.17） | 1.40 | 3.59 | 2.68 | 0.72 | 0.135 | 0.035 | 7.9 / 1.07 |
  | c 双卡同步 | 1,024 | 1.89 | 2.35（0 + 2.04 + 0.11） | — | 4.27 | 2.49 | 0.77 | 0.127 | 0.014 | 7.9 / 1.07 |
  | d 单卡重叠 + 解耦 | 1,104 | 3.48 | 3.94（0.69 + 2.99 + 0.16） | 0.49 | 3.96 | **5.10** | 0.70 | 0.132 | 0.036 | 8.6（同一卡） |

  - 重叠时整份 rollout 都由上一份权重采（`stale_share` 1：collect 比 update 短），kl 列因此比同步高（它量的是行为策略到新策略）；解耦目标下 clip_frac 与同步相同（0.135 对 0.133），普通比率（e）翻到 0.33，与 B11 一致，不建议用。
  - 双卡同步（c）= 单卡同步（a）：交接和换权重的代价看不出来（各 < 1 ms 主机时间、8–10 ms 换权重）。actor 卡上 torch 只占 1.07 GB（nvidia-smi 1.7 GB）。
  - 双卡确实去掉了 GPU 争用：单卡重叠（d）actor 一次调用 5.1 ms、collect 3.5 s；双卡（b）2.7 ms、2.2 s。
  - **但只快了 16%（1,051 → 1,216×），远低于预期的 max(collect, update)**。瓶颈是**主机线程**：学习器的 PPO 部分单独跑 1.99–2.04 s（a、c），和 actor 同时跑时 2.72 s（b）/ 2.93 s（e，没有重算可以"垫"在前面）；按 e 估算，actor 采集的那 2.2 秒里学习器只有单独时 40–50% 的速度，rollout 满了 actor 停下等（`wait_learner` 1.1–1.4 s，worker 也停）以后才全速。actor 这边 collect 从 1.86 涨到 2.18 s（+17%），推理没变慢（2.44 → 2.68 ms），也是主机侧。整个训练器进程只用 1.8–2.4 个核（`c_trainer_cores`）：两个 Python 线程共用一把 GIL，B18 已知学习器是主机线程限速的。线程切换间隔（f）没有影响。重算价值（`--decoupled 1` 的 0.6 s）在重叠里是真成本，但去掉它（e）也只换来 +7% 且裁剪翻倍。
  - 推论：要拿到 max(collect, update)，学习器必须离开 actor 的进程（或 actor 离开），不是再加卡。本配置下学习器单独 2.3 s + 重算约 0.45 s ≈ 2.8 s 对 collect 1.9–2.2 s，周期约 2.8 s，约 **1,550×**（无搜索）；C99 全配置时 actor 线程还要跑 lane 服务（B36），GIL 的争用只会更重。
- **负载事故**（主机 A，10-17 09:08–09:33 UTC）：第一次吞吐测试用 C99 的全部标志（64 worker，含死亡教师和反事实搜索，`--teacher-fork 1`）。前 4 分钟正常（负载 40–48，974–982×）；09:13 起负载 45 → 175（配额 128 核，但主机 CPU 80% 空闲、11.7% 系统态、200 个僵尸、大量只活零点几秒的游戏进程；`nr_throttled` 只有 9），两边的 `w_fork` 都涨到每周期 90–220 s，我的运行掉到 113–158×（collect 25–35 s），**C99 u22995–u23024 共 30 次更新中位 119×（平常 768×），约 18 分钟**（损失约 15 分钟的 C99 吞吐）。`pgrep` / `ps` 读 `/proc/<pid>/cmdline` 卡住数分钟（正在 fork 的进程持有 mm 锁），改用 `/proc/*/comm` 找到 pid 后先停驱动脚本再 SIGINT 训练器（正常存 `last.pt` 退出），C99 从 u23026 起回到 711–761×，没有遗留孤儿游戏进程。同一时段 09:16–09:30 C99 的 watcher 在评 u23000（8 worker），也可能有份。原因没有查实：负载在搜索开始后才起来，8 worker 冒烟和无搜索的 64 worker 运行都在 40–60，候选是第二个 64 worker 训练器的搜索子进程（fork 大进程）在内核层面的争用，而不是 CPU 配额。教训：C99 全配置的第二个训练器不能和 C99 同机；之后的测试都加了负载守护。
- **结论**：
  - `--learner-device` 本身正确且便宜（逐位测试、冒烟、六个变体 0 个 Traceback；交接 248 MiB/次走 NVLink、异步；换权重约 9 ms），去掉了 GPU 争用（推理 5.1 → 2.7 ms），双卡重叠 + 解耦比单卡同步快 16%、比单卡重叠快 10%，学习数字（clip_frac、ev）与同步一致。
  - 没有达到 1,500×：训练器是单进程两线程，限速的是 GIL / 主机线程，不是 GPU。下一步（B38 第二步，建议）：学习器放进独立进程（spawn；rollout 的主机数组走共享内存，镜像和权重走 CUDA IPC 或按现在的方式在两卡间拷），预期回到 max(collect, update + 重算) ≈ 2.8 s。
  - 没测：C99 全配置（搜索与 lane 开着）下的双卡重叠——在主机 A 上和 C99 同跑不安全；要在 C99 停的时候或另一台主机上测。


### B38 第二步：学习器放进独立进程（`--learner-process 1`）（2026-10-17，代码完成，未上线）

**实验目的**

第一步的结论是双卡重叠只快 16%：actor 和学习器是同一个 Python 进程里的两个线程，共用一把 GIL，学习器在 actor 采集时只有单独时 40–50% 的速度。第二步把学习器放进独立进程，让重叠成为真的重叠，目标是无搜索配置下 ~1,400× 以上，并估算 C99 全配置（搜索开着）能到多少。

**实验方法**

- **代码**（分支 `b38-learner-device`：`a0db823` 主体，`748d31f` memfd 经 libc，`e2d8f03` 训练器进程关可扩展显存段，`3691e58` 测试，`0f66e1c`–`661aa57` 脚本；opus 子代理实现，未合入 abplus-training）：
  - `--learner-process 1`（要求 `--learner-device` 是另一块卡；同卡两进程即 B13 的崩溃类，直接拒绝）。训练器进程用 spawn 起一个学习器进程（`learner_child_entry` → `main(argv, child=…)`：同样的参数、同样的建模与 `learn()` 闭包，跳过采样器、actor 模型、GraphActor、lane、快照）。学习器进程拥有 `learner_model`、两个优化器、`learn()`、检查点、progress.csv 与每次更新的打印、teacher v2 / cf 蒸馏环；训练器进程保留采样器、worker、GraphActor、lane 服务、快照、局记账。
  - **rollout 交接不经主机拷贝**：两份 rollout 的主机数组用 memfd 共享内存分配（`SharedArrays`，`Rollout(..., alloc=)`；不受 /dev/shm 4 GB 限制，页按写入分配，与 numpy 的 zeros 相同；本机 Python 缺 `os.memfd_create`，经 libc 调用），学习器进程经 `/proc/<pid>/fd` 映射；温度张量（K/V、o）和权重缓冲在启动时经 CUDA IPC 交给学习器进程（池增长时随下一个作业重发）。每个作业只经队列发小元数据（计数、局列表、教师记录、worker 统计快照、prof、lane 统计、actor 显存）。actor 在发消息前已同步自己的流（与第一步同），学习器收到后在自己的流对上把用到的行拷到学习器卡（第一步的 `hand_off`）。actor 在收到读这份 rollout 的那次更新的 `fresh` 之前不会重写它；学习器在 `fresh` 之后不再读它（`t_rooms_new` 挪到 `fresh` 之前计算：日志列，所有模式，顺带修掉第一步注意到的旧竞态）。
  - **权重回传**：学习器把参数按字节拼进自己卡上的一块缓冲，一次对等拷贝写进 actor 卡上的 IPC 缓冲，同步自己的流后发 `fresh` 消息并置进程间事件；actor 在 `take_weights` 时读消息（`pf_p`、更新计数），再用 `_foreach_copy_` 写回参数。`--overlap`、`busy`、`version`、`sampler.control[3]` 的语义不变（一份 rollout 的滞后）。
  - **故障**：学习器异常 → `error` 消息（含回溯）+ 事件，actor 抛出并正常收尾；actor 停止（结束、SIGINT、异常）→ 停止消息，学习器做完当前更新、存 `last.pt`、发 `done`；actor 被杀 → 学习器每秒查父进程，发现消失就存 `last.pt` 退出。学习器进程忽略 SIGINT / SIGTERM（Ctrl-C 和 timeout 会发给整个进程组）。
  - 容器里 CUDA IPC 不能用可扩展显存段（`pidfd_getfd: Operation not permitted`，没有 ptrace 权限）：`--learner-process 1` 时训练器进程开头关掉可扩展段（`ipc_safe_allocator`，学习器进程照旧）。
  - 新列（仅进程模式）：`handoff_q_s`（消息排队）、`handoff_gpu_ms`（镜像拷贝的 GPU 时间）、`publish_s`（学习器发布权重）、`c_learner_cores`（学习器进程的核数；`c_trainer_cores` 是训练器进程自己的）。关闭此开关时单进程路径不变（数值同第一步）；`gains_on` 取代 `book.gains is not None`（同一条件）。
  - 测试辅助：`ISAAC_RL_B38_FAIL_AT=k` 让学习器进程在第 k 次更新前抛异常。
- **测试**：`tests/test_learner_device_smoke.py` 加两节，共 11 项全过（主机 A GPU 1、2）：(d) SharedArrays 上的 rollout 与 numpy 的逐位相同；spawn 出的进程映射后学习器分块前向与父进程逐位相同、它的写入父进程看得见；(e) 子进程经 CUDA IPC 收到 cuda:0 的 rollout 张量，`hand_off` 到 cuda:1 的行逐位相同、房间表相同；它把另一组权重写进 IPC 缓冲再置事件，父进程 foreach 拷贝后与之逐位相同。原 10 个冒烟测试在最终代码（`661aa57`）上全过（360 项）。
- **真机**（主机 A，`ws14`，只用 GPU 1、2，**全部不带搜索**：无 `--teacher`、`--cf 0`，负载守护 85）：冒烟（8 worker、1.5 游戏小时、从零）g（进程 + 重叠 + 解耦）、h（进程、同步）、a、b；故障三项：`fail`（第 3 次更新前注入异常）、`int`（240 秒时 SIGINT）、`kill`（第 5 次更新后 SIGKILL 训练器进程）；吞吐两组（tput2：a、b 为第一步数据，g 为第二步；tput3：a、b、g 在同一时段重跑），64 worker、从 `segment1-final.pt` 续 60 次更新，取第 9–61 次的中位数。

**实验结果**

- **冒烟**（0 个 Traceback；第 5 次更新）：g 293×、kl 0.0038、ev 0.65；h 202×、kl 0.0005、ev 0.77；a 202×、kl 0.0022、ev 0.57；b 361×、kl 0.0065、ev 0.59。
- **故障**：
  - `fail`：训练器以 `RuntimeError: learner process: … injected failure before update 3`（附学习器的回溯）结束，`finished 2 updates`，学习器存了 `last.pt`，没有卡住，没有孤儿游戏进程。

  - g 比单卡同步快 **44–52%**，比线程重叠快 25–28%。PPO 部分回到单独时的 2.0–2.1 s（线程模式 2.7–2.8 s），collect 回到同步时的 1.8 s（线程模式 2.2 s），推理 2.4 ms 不变：GIL 争用消失。
  - 训练器的核数：训练器进程 0.65 核 + 学习器进程 2.1–2.2 核。
  - **延迟**（g 的中位数）：作业消息排队 1.1 ms，学习器发起交接 0.6–0.7 ms，镜像拷贝在 GPU 上 1.0 ms（248 MiB，NVLink 约 240 GB/s），学习器发布权重（拼字节 + 对等拷贝 + 同步）2.4–2.5 ms，actor 取权重（foreach 拷贝 + 同步）1.3–1.5 ms。
  - 现在限速的是学习器：周期 = update 2.8–2.9 s，其中 0.58 s 是 `--decoupled 1` 的重算；actor 每周期等学习器约 1.0 s（worker 空等 0.66）。要到 2,000×（周期约 2.2 s）得让学习器更快（重算、PPO 本身），不是再拆进程。
- **对 C99 全配置的估计**（搜索与 lane 开着，未测）：C99 现在同步 collect 2.7 s、update 2.9–3.0 s、约 765×。进程模式下 actor 不再和学习器抢 GIL，collect 约保持 2.7 s；学习器 = 现在的 update 约 3.0 s + 重算约 0.6 s ≈ 3.6 s，成为周期 → 32,768 × 4 / 30 / 3.6 ≈ **1,200×（约 1,100–1,250×，+45–65%）**。不确定处：重叠后 worker 不再在更新期间停住，教师 / 反事实搜索（`--teacher-share 0.1`）要从采集时间里让出，collect 可能变长；cf 蒸馏记录随每个作业经队列序列化（大小未测）。
- **结论**：学习器独立进程正确（逐位测试、冒烟、故障三项、两组吞吐 0 个 Traceback），无搜索时 1,515–1,539×，达到目标；全配置预计约 1,200×，需在 C99 不在的主机上验证。
- 没测：C99 全配置；GRU 记忆模型和非温度模型的进程模式；rollout 池增长时重发 IPC 张量的路径（实测从未触发）；分支、build lab、学习器 bench 在进程模式下直接拒绝。
